# 💻 День 27 · 2026-11-10 · ai: RAG — как построить поиск по документации проекта

**Коротко:** RAG (Retrieval-Augmented Generation) — это «сначала найди, потом ответь»: перед вызовом LLM система достаёт из ваших документов несколько релевантных фрагментов и кладёт их в промпт. Качество такого бота почти целиком определяется не моделью, а поиском: как нарезаны документы, как они ищутся и как вы измеряете, что нашлось нужное.

### Сначала вопрос: а нужен ли RAG вообще?

Контекстные окна современных моделей — сотни тысяч токенов. Если вся документация проекта (README, ADR, гайд по код-стайлу, описание архитектуры) влезает примерно в 200 тыс. токенов, Anthropic в статье про Contextual Retrieval прямо советует **не строить RAG, а положить всё в промпт** и включить prompt caching: кешированный префикс стоит в разы дешевле и отвечает быстрее. Второй вариант без векторной базы — **агентный поиск**: модель сама вызывает `grep`, читает файлы и уточняет запрос (так работают Claude Code и похожие агенты в репозитории). Для кода это часто лучше эмбеддингов, потому что имена символов точные.

RAG нужен, когда корпус большой и разнородный (Confluence, тикеты, Storybook, OpenAPI, постмортемы за пять лет), когда важны права доступа к документам и когда ответ должен быть быстрым и дешёвым на тысячах запросов в день.

### Пайплайн: два конвейера

**Индексация (офлайн, в CI):** собрать документы → нарезать на чанки → обогатить контекстом → посчитать эмбеддинги и полнотекстовый индекс → сохранить с метаданными (путь, заголовок, дата, команда, права). **Запрос (онлайн):** переформулировать вопрос → гибридный поиск (векторы + BM25) → слить результаты → переранжировать → отдать модели топ-5…20 чанков с источниками → ответ с цитатами.

Нюансы, на которых спотыкаются чаще всего:

- **Чанкинг по структуре, а не по символам.** Markdown режьте по заголовкам (`##`, `###`), код — по функциям или классам, OpenAPI — по эндпоинтам. Чанк в 300–800 токенов с небольшим перекрытием — разумный старт. Кусок «...и поэтому мы отказались от него в пользу...» без заголовка бесполезен.
- **Контекст чанка.** Фрагмент «Таймаут — 30 секунд» ничего не значит без «чей таймаут». Приём *Contextual Retrieval*: при индексации дешёвая модель дописывает к каждому чанку 1–2 предложения, к какому документу и разделу он относится. По замерам Anthropic это снижает долю неудачных поисков на 35% (только эмбеддинги), на 49% вместе с контекстным BM25 и на 67% с реранкингом. Простая версия того же — приклеить к чанку «хлебные крошки» заголовков: `Архитектура › Auth › Refresh-токены`.
- **Гибридный поиск.** Эмбеддинги хорошо ловят смысл («как обновить токен» ≈ «refresh flow»), но плохо — точные строки: `ERR_AUTH_042`, `provideHttpClient`, номер тикета. BM25 (классический полнотекстовый поиск) — наоборот. Ищите обоими способами и сливайте через **Reciprocal Rank Fusion**: каждому документу сумма `1 / (60 + место в выдаче)` по обоим спискам. Это проще, чем подбирать веса.
- **Реранкинг.** Достаньте 50–150 кандидатов дёшево, затем cross-encoder-реранкер (или сама LLM) пересортирует их, глядя на пару «вопрос + чанк» целиком. Это самый дешёвый крупный прирост качества.
- **Свежесть и права.** Индекс устаревает с первым мёржем: переиндексация в CI по изменённым файлам. Фильтр по правам — **до** поиска (в SQL `WHERE`), а не после генерации: иначе модель перескажет закрытый постмортем.

### Пример: гибридный поиск на Postgres + pgvector

Отдельная векторная БД не обязательна: если у команды уже есть Postgres, `pgvector` + встроенный полнотекстовый поиск закрывают 90% задач.

```ts
// Чанкинг markdown по заголовкам с «хлебными крошками»
export function chunkMarkdown(path: string, md: string) {
  const chunks: { path: string; breadcrumb: string; text: string }[] = [];
  const trail: string[] = [];
  let buf: string[] = [];
  const flush = () => {
    const text = buf.join('\n').trim();
    if (text) chunks.push({ path, breadcrumb: trail.join(' › '), text });
    buf = [];
  };
  for (const line of md.split('\n')) {
    const m = /^(#{1,3})\s+(.*)/.exec(line);
    if (m) { flush(); trail.length = m[1].length - 1; trail.push(m[2]); }
    else buf.push(line);
  }
  flush();
  return chunks; // в эмбеддинг идёт `${breadcrumb}\n\n${text}`
}
```

```sql
-- Гибридный поиск + Reciprocal Rank Fusion (k = 60)
WITH vec AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $1) AS r
  FROM doc_chunks WHERE team = ANY($3)          -- права ДО поиска
  ORDER BY embedding <=> $1 LIMIT 50
), kw AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
  FROM doc_chunks, websearch_to_tsquery('simple', $2) q
  WHERE tsv @@ q AND team = ANY($3)
  ORDER BY ts_rank_cd(tsv, q) DESC LIMIT 50
)
SELECT id, SUM(1.0 / (60 + r)) AS score
FROM (SELECT * FROM vec UNION ALL SELECT * FROM kw) t
GROUP BY id ORDER BY score DESC LIMIT 20;      -- дальше реранкер
```

В промпт чанки идут в тегах `<document>` с путём, а инструкция требует отвечать только по ним, ссылаться на путь и честно говорить «в документации этого нет» (про структуру промпта — урок 2026-11-03).

### Как понять, что работает

Соберите **20–50 реальных вопросов** из Slack и онбординга и для каждого отметьте, какой документ правильный. Метрика поиска — *recall@k*: в скольких вопросах правильный чанк попал в топ-k. Её считают без LLM, за секунды, и прогоняют при каждом изменении чанкинга или модели эмбеддингов. Качество ответа (верность источникам, полнота) — отдельный слой оценки, о нём будет урок про evals.

**Зачем это тимлиду:** «бот по документации» — частый запрос сверху, и самая частая ошибка — начать с выбора векторной БД. Ваша работа — задать вопросы в правильном порядке: влезает ли всё в контекст, где лежит правда, кто имеет доступ, как мы измерим качество. И помнить, что RAG вскрывает проблему документации: если ADR не написаны, поиск найдёт устаревший Confluence.

**Применить завтра:**

- Посчитайте объём документации команды в токенах. Если меньше ~200 тыс., сделайте прототип «всё в промпт + кеширование» за день, без RAG.
- Попросите команду за неделю скинуть в тред 30 вопросов, которые задают новички. Это и будет ваш eval-набор для любого будущего решения.
