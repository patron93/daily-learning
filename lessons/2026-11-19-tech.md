# 💻 День 36 · 2026-11-19 · classic: «The Pragmatic Programmer» — идеи, которые работают в команде

**Коротко:** книга Дэйва Томаса и Энди Ханта вышла в 1999 году, а в 2019-м авторы почти полностью переписали её к 20-летию (второе издание, 100 советов). Сегодня не пересказ, а семь идей, которые тимлиду полезнее всего: ETC как главный критерий дизайна, правильное понимание DRY, ортогональность, обратимость, tracer bullets, разбитые окна и «не обгоняй свои фары».

**ETC — Easier To Change.** Во втором издании авторы признались, что почти все принципы дизайна (SOLID, слабая связность, инкапсуляция, именование) — частные случаи одного: хороший дизайн легче менять, чем плохой. Это не замена SOLID, а вопрос, который можно задать на любом ревью: «Если завтра требование X поменяется, сколько файлов придётся тронуть?» Ценность ETC в том, что он понятен и джуну, и продакту: «мы сделали так, чтобы смену платёжного провайдера можно было сделать за день» — это аргумент, а «здесь нарушен DIP» — нет. Когда не знаешь, что изменится, авторы советуют делать код **заменяемым** и записывать в заметки, где ты угадывал: через год будет видно, насколько хорошо команда предсказывает изменения.

**DRY — про знание, а не про одинаковые строки.** Самое неправильно понятое правило в индустрии. В книге DRY звучит так: у каждого кусочка *знания* должно быть одно авторитетное представление. Два одинаковых по тексту валидатора, проверяющих разные бизнес-правила, — не дублирование, и их склейка в «универсальную» функцию с флагами создаёт связность, которой в предметной области нет. А вот правило «цена показывается с НДС и округлением до гроша», размазанное по трём компонентам, — дублирование, даже если код выглядит по-разному. К DRY авторы относят и дублирование между документацией и кодом, между API и клиентом (отсюда генерация клиентов из OpenAPI), и **дублирование между людьми**: две команды, решающие одну задачу, потому что не знают друг о друге.

**Ортогональность и обратимость.** Ортогональные компоненты не влияют друг на друга: поменял один — второй не заметил. Проверка простая: «если я поменяю это, сколько модулей сломается?» Обратимость — следствие: «нет окончательных решений». Фреймворк, облако, стейт-менеджер, вендор аналитики — всё это когда-то будут менять, поэтому сторонние зависимости держат за своими интерфейсами (Adapter и Facade из урока 2026-10-29), а архитектурные решения фиксируют так, чтобы их можно было пересмотреть.

**Tracer bullets против прототипов.** Трассирующие пули показывают, куда летит очередь, в реальном времени. В коде это тонкий срез фичи **через все слои**, который работает с первого дня: маршрут, компонент, сервис, настоящий эндпоинт, запись в БД — пусть с одним полем. Этот код остаётся и обрастает функциональностью; зато интеграционные проблемы видны в первую неделю, а не в последнюю. Прототип — другое: он отвечает на один вопрос (удобен ли UX, тянет ли библиотека 10 000 строк в таблице) и **выбрасывается**. Главная ошибка — смешать их: прототип на моках, который «чуть допилили» и отправили в прод.

**Разбитые окна.** Один закомментированный тест, один `any`, одно «временное» `// TODO` в main — и команда считывает сигнал «здесь можно». Авторы ссылаются на теорию разбитых окон: запущенность заразна. Тимлиду это даёт простое правило: разбитое окно нельзя оставлять без реакции — либо чинишь, либо хотя бы «заколачиваешь доской» (тикет, `eslint-disable` с причиной и ссылкой). Рядом в книге — «каменный суп и варёная лягушка»: изменения легче продвигать маленьким работающим примером, чем большой презентацией, и следить за медленной деградацией, которую никто не замечает.

**Не обгоняй свои фары.** Делай шаги такого размера, чтобы получить обратную связь до следующего: маленькие PR, фичефлаги, частые релизы. Чем дальше прогноз, тем он хуже, поэтому «спроектируем на два года вперёд» почти всегда проигрывает «сделаем так, чтобы было легко поменять». А «не программируй по совпадению» дополняет: если код работает, а ты не понимаешь почему (тест зелёный, потому что `setTimeout` удачно совпал с `detectChanges`), он сломается в самый неподходящий момент.

```ts
// ❌ «DRY» по тексту: склеили разные знания в одну функцию
function validateCode(value: string, kind: 'postal' | 'branch') {
  return /^\d{2}-\d{3}$/.test(value); // сегодня совпало, завтра у филиалов будет 6 цифр
}

// ✅ Два правила домена — два валидатора, даже если сейчас они похожи
export const polishPostalCode = Validators.pattern(/^\d{2}-\d{3}$/);
export const branchCode = Validators.pattern(/^\d{2}-\d{3}$/); // формат из CRM, меняется отдельно

// ✅ А настоящее дублирование знания — в одно место
@Pipe({ name: 'grossPrice' })
export class GrossPricePipe implements PipeTransform {
  private readonly vat = inject(VAT_RATE);
  transform(net: number): number {
    return Math.round(net * (1 + this.vat) * 100) / 100;
  }
}
```

**Зачем это тимлиду:** у книги нет фреймворка или процесса — это словарь для разговора о качестве. «Это разбитое окно», «давай пустим tracer bullet», «это два разных знания, не склеивай» — короткие формулы, которые экономят полчаса спора на ревью и которые можно повесить в CONTRIBUTING.md. Отдельная глава про **knowledge portfolio** (регулярно «инвестировать» в знания, диверсифицировать, ребалансировать) — готовая рамка для разговора о развитии на 1:1.

**Применить завтра:**

- На ближайшем планировании большой фичи предложи сначала tracer bullet: срез «маршрут → компонент → API → БД» с одним полем в первые 2–3 дня, до UI-полировки.
- Заведи метку `broken-window` в трекере и раз в спринт выдели час, чтобы закрыть 2–3 таких тикета: выключенные тесты, `any`, игнорируемые ворнинги.
