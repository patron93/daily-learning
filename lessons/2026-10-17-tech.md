# 💻 День 3 · 2026-10-17 · news: lockfile для GitHub Actions

**Коротко:** 14 октября GitHub выпустил в public preview lockfile для workflow: файл `.github/workflows/actions.lock` фиксирует точный коммит каждого action, включая транзитивные зависимости. В YAML можно и дальше писать `actions/checkout@v4`, но запускаться будет ровно тот код, который вы залочили.

**Что случилось.** Ссылка вида `uses: some/action@v3` указывает на тег, а тег в Git можно передвинуть. Ровно так в марте 2025 года взломали `tj-actions/changed-files`: атакующий переписал теги на вредоносный коммит, и тысячи репозиториев на следующем запуске CI начали печатать секреты в логи. Раньше защита была одна: пинить каждый action по полному SHA прямо в workflow. Это нечитаемо, неудобно обновлять, а главное, не спасает от транзитивных зависимостей: composite action, который вы запинили, внутри всё равно может ссылаться на чужой action по тегу.

**Как это устроено.** Lockfile генерирует расширение `gh actions-lock`. Это YAML с двумя разделами: `workflows` (какой файл какие actions использует) и `dependencies` (ref, коммит, плюс `owner_id` и `repo_id` исходного репозитория). Числовые id нужны, чтобы при запуске проверить, что за именем `owner/repo` стоит тот же репозиторий, а не пересозданный злоумышленником после переименования. После онбординга workflow каждая его зависимость обязана быть в lockfile. Dependabot, обновляя версию action, сам перегенерирует запись в том же PR. Администраторы организации или репозитория могут включить политику **Require lockfile** (тоже preview). Доступно на Free, Team и Enterprise Cloud.

```bash
gh extension install github/gh-actions-lock
gh actions-lock            # сканирует .github/workflows/, пишет actions.lock
gh actions-lock --relock   # тег легитимно переехал (новый релиз) → перезалочить
git add .github/workflows && git commit -m "ci: lock actions"
```

```yaml
# .github/workflows/actions.lock (фрагмент)
version: 'v0.0.2'
workflows:
    '.github/workflows/ci.yml':
        - 'actions/setup-node@v4'
dependencies:
    'actions/setup-node@v4':
        ref: 'v4'
        commit: '…полный SHA…'
        owner_id: …        # числовой id владельца
        repo_id: …         # числовой id репозитория
```

Нюансы, которые легко пропустить: lockfile не проверяет, безопасен ли сам action, он только гарантирует, что запустится именно отревьюенный код. Зависимости reusable workflows покрывает lockfile того репозитория, где reusable workflow определён, а не ваш. И это preview: формат (`version: v0.0.2`) ещё может поменяться.

**Зачем это тимлиду:** CI фронтенд-команды обычно держит токены npm-реестра, деплой-ключи и доступ к облаку, а workflow-файлы ревьюят меньше всего. Lockfile превращает «какой код крутится в нашем CI» из неявного состояния тегов в обычный файл в репозитории, который проходит code review и виден в диффе. Это та же логика, что `package-lock.json`, только для пайплайна.

**Применить завтра:**

- Прогоните `gh actions-lock` на одном самом «секретном» workflow (деплой или публикация пакетов), посмотрите дифф и закоммитьте. Остальные workflow можно онбордить по одному.
- Договоритесь в команде: изменения в `actions.lock` ревьюят как изменения зависимостей, а не «апрув не глядя». Если Dependabot для GitHub Actions ещё не включён, включите: он будет обновлять lockfile сам.
