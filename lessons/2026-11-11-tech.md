# 💻 День 28 · 2026-11-11 · backend: Аутентификация — сессии vs JWT, OAuth2/OIDC, PKCE и BFF

**Коротко:** в августе 2026 IETF выпустила [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html) (BCP 212) «OAuth 2.0 for Browser-Based Applications». Её главный вывод для Angular-команд: для приложений с бизнес- и персональными данными токены в браузере держать не стоит — рекомендуемый паттерн **BFF**, а браузер получает только `HttpOnly`-cookie сессии. Разберём, как к этому пришли и что из «JWT в localStorage» пора убирать.

**Сессии vs JWT — на самом деле спор о другом.** Сессия — это непрозрачный ID в cookie, состояние на сервере (Redis/БД): отозвать доступ — удалить запись. JWT — самодостаточный подписанный токен: сервер проверяет подпись без похода в хранилище, поэтому JWT удобен **между сервисами**. Но у JWT две цены: его нельзя отозвать до истечения `exp` (отсюда короткий срок жизни и refresh-токены), а в браузере его надо где-то хранить. `localStorage` читается любым скриптом на странице, поэтому одна XSS (или скомпрометированная npm-зависимость) — и токен ушёл с машины пользователя. Cookie с `HttpOnly` скрипт не прочитает. Правильная постановка вопроса: не «сессии или JWT», а **«где живёт токен и кто может его прочитать»**.

**OAuth2, OIDC, PKCE — кто за что отвечает.** OAuth2 — делегирование *доступа* (access token к API). OIDC — слой поверх него про *личность*: `id_token` и `userinfo`, «кто вошёл». Для браузерных и мобильных клиентов единственный нормальный flow — **Authorization Code + PKCE**: клиент генерирует случайный `code_verifier`, в редирект отправляет только его хеш (`code_challenge`, метод `S256`), а при обмене кода на токены предъявляет оригинал. Перехваченный код без verifier бесполезен. Implicit flow и Resource Owner Password RFC 10017 относит к устаревшим паттернам.

![Три паттерна RFC 10017: BFF, token-mediating backend, браузерный клиент](/img/tech/2026-11-11-oauth-bff.svg)

**Три архитектуры из RFC 10017 (от безопасной к рискованной).** (1) **BFF** — бэкенд сам является *confidential client*, хранит токены у себя, браузеру отдаёт cookie сессии (`Secure`, `HttpOnly`, рекомендованы `SameSite=Strict` и префикс `__Host-`) и проксирует запросы к API. (2) **Token-mediating backend** — бэкенд получает токены, но access token отдаёт в браузер, тот ходит в API напрямую; вариант, когда проксировать всё нельзя. (3) **Браузерный OAuth-клиент** (типичный `angular-oauth2-oidc` / `oidc-client-ts` в SPA) — публичный клиент, PKCE обязателен, refresh-токены должны ротироваться при каждом использовании или быть привязаны к отправителю (DPoP), с ограниченным сроком жизни. Он уязвим ко всем атакам из документа: XSS не обязательно крадёт токен — она может просто запустить новый flow от имени пользователя.

```ts
// Angular за BFF: в коде нет ни одного токена
export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(
      withFetch(),
      // BFF ставит cookie XSRF-TOKEN, Angular кладёт её в заголовок на мутирующих запросах
      withXsrfConfiguration({ cookieName: 'XSRF-TOKEN', headerName: 'X-XSRF-TOKEN' }),
    ),
  ],
};

@Injectable({ providedIn: 'root' })
export class Auth {
  // BFF знает сессию по HttpOnly-cookie и отдаёт только claims для UI
  readonly user = httpResource<User | null>(() => '/bff/user');
  login(returnUrl = location.pathname) {
    location.href = `/bff/login?returnUrl=${encodeURIComponent(returnUrl)}`; // PKCE делает BFF
  }
  logout() { location.href = '/bff/logout'; }
}
```

**Что ломается на практике.** Cookie-сессия возвращает в игру CSRF — поэтому `SameSite` плюс XSRF-заголовок. BFF должен жить на том же сайте, что и SPA (обычно `/bff` на том же домене через reverse proxy), иначе `SameSite=Strict` и third-party cookie блокировки браузеров всё сломают. И BFF — это ещё один сервис, который надо масштабировать и мониторить; для внутренней админки с SSO иногда честнее остаться на браузерном клиенте с PKCE, но осознанно и с ротацией refresh-токенов.

**Зачем это тимлиду:** решение об auth-архитектуре — это решение о радиусе поражения от XSS и supply-chain атак, а не про библиотеку. Теперь у тебя есть ссылка на BCP от IETF, а не «мнение фронтенда», чтобы обсуждать это с бэкендом и безопасниками.

**Применить завтра:**

- Поищи в проекте `localStorage.setItem(` и `sessionStorage` рядом со словами token/jwt. Если нашлось — заведи ADR: BFF, token-mediating или осознанный браузерный клиент с ротацией refresh-токенов и коротким `exp`.
- Проверь, что в конфиге IdP для SPA выключены implicit flow и password grant, а PKCE (`S256`) обязателен.
