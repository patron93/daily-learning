# 💻 День 7 · 2026-10-21 · classic: SOLID на примерах Angular

**Коротко:** SOLID в Angular — это не про «интерфейс на каждый сервис», а про то, как DI, токены и композиция компонентов позволяют менять поведение, не переписывая существующий код. Пять принципов полезны как язык для ревью: «тут две причины для изменения», «этот провайдер нарушает контракт», а не «мне не нравится».

**S и I: границы ответственности.** У Роберта Мартина SRP звучит не как «класс делает одну вещь», а как «у модуля одна причина для изменения» — точнее, один *актор* (бизнес-роль), который может потребовать изменений. Компонент, который сам ходит в HTTP, хранит состояние фильтров, форматирует даты и рисует таблицу, меняется по просьбе бэкенда, продукта и дизайнера одновременно — отсюда конфликты в PR и хрупкие тесты. Типовой разрез в Angular: контейнер (подключает store/сервис), презентационный компонент (только `input()`/`output()`), store или facade на сигналах, pipe для форматирования. ISP — та же идея со стороны потребителя: не заставляйте зависеть от того, что не используется. Признаки нарушения: `UserService` на 40 методов, который инжектят ради одного `currentUser`, или компонент, принимающий целый `User`, хотя рисует только имя и аватар. Узкий input — это ещё и бесплатная производительность при OnPush: меньше поводов для перерисовки.

**O и D: DI как механизм расширения.** OCP в Angular почти всегда реализуется через DI: новое поведение — новый провайдер, а не новый `if` в старом сервисе. Классика — `multi: true` у `InjectionToken`: несколько реализаций регистрируются независимо, потребитель получает массив. Так устроены `APP_INITIALIZER`/`provideAppInitializer`, валидаторы форм и функциональные интерцепторы через `withInterceptors([...])`. Для компонентов OCP — это content projection и `ng-template`: таблица, принимающая шаблон ячейки, расширяется без правки её кода. DIP: высокоуровневый код зависит от абстракции, а конкретику выбирает место сборки (`app.config.ts`, routes, тесты). Нюанс TypeScript: интерфейсы стираются при компиляции, поэтому токеном DI служит **абстрактный класс** или `InjectionToken`. Абстрактный класс удобнее: он одновременно тип и токен, `inject(Logger)` без дженериков.

**L: контракт важнее наследования.** LSP в Angular нарушают не столько наследованием компонентов (его лучше избегать вообще: `host directives` и композиция надёжнее), сколько подменой провайдеров. `useClass: LocalStorageCache` вместо `MemoryCache` ломает SSR, потому что на сервере нет `localStorage`; мок в тесте возвращает значение синхронно, а реальный сервис — асинхронно, и тест «зелёный» на неправильном поведении. Правило: у абстракции должен быть описан контракт (синхронность, ошибки, побочные эффекты), и каждая реализация его соблюдает. Обратная сторона SOLID — оверинжиниринг: абстракция под единственную реализацию без второго потребителя на горизонте — это YAGNI, а не DIP.

```ts
// D + O: абстракция как токен и расширяемый набор стратегий
export abstract class ReportExporter {
  abstract readonly format: 'csv' | 'xlsx' | 'pdf';
  abstract export(rows: readonly ReportRow[]): Promise<Blob>;
}

export const REPORT_EXPORTERS =
  new InjectionToken<readonly ReportExporter[]>('REPORT_EXPORTERS');

// app.config.ts — новая выгрузка = новая строка, сервис не трогаем
export const appConfig: ApplicationConfig = {
  providers: [
    { provide: REPORT_EXPORTERS, useClass: CsvExporter, multi: true },
    { provide: REPORT_EXPORTERS, useClass: XlsxExporter, multi: true },
  ],
};

@Injectable({ providedIn: 'root' })
export class ReportService {
  private readonly exporters = inject(REPORT_EXPORTERS);

  readonly formats = this.exporters.map((e) => e.format);

  export(format: ReportExporter['format'], rows: readonly ReportRow[]) {
    const exporter = this.exporters.find((e) => e.format === format);
    if (!exporter) throw new Error(`No exporter for ${format}`);
    return exporter.export(rows);
  }
}
```

```ts
// I: презентационный компонент получает ровно то, что рисует
@Component({
  selector: 'app-user-badge',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<img [src]="avatarUrl()" alt="" /> {{ name() }}`,
})
export class UserBadge {
  readonly name = input.required<string>();
  readonly avatarUrl = input.required<string>();
}
```

**Зачем это тимлиду:** SOLID даёт команде общий словарь для архитектурных споров на ревью и помогает решить, *где* проходят границы фич в монорепо: абстракция (`AuthFacade`, `ReportExporter`) живёт в domain/api-библиотеке, реализации — в feature/data-access, а сборка — в приложении. Это напрямую поддерживает правила `enforce-module-boundaries` из урока про Nx. И наоборот, умение сказать «здесь абстракция лишняя» экономит команде недели на поддержке слоёв, которые никто не расширяет.

**Применить завтра:**

- На ближайшем ревью задайте вопрос про SRP в форме «кто попросит изменить этот файл?» — если в ответе больше одной роли (бэкенд, продукт, дизайн), предложите разрез контейнер/презентация/store.
- Найдите в проекте один `if (type === ...)`, разрастающийся с каждой фичей (экспорт, платёжные методы, виджеты дашборда), и переведите его на `InjectionToken` с `multi: true` — новая реализация станет новым провайдером, а не правкой общего сервиса.
