# 💻 День 32 · 2026-11-15 · news: Angular 20 теряет LTS 28 ноября, а мажоры теперь раз в год

**Коротко:** через 13 дней, **28 ноября 2026**, у Angular 20 заканчивается LTS: больше никаких патчей, включая security. Одновременно это первая осень нового режима: Angular перешёл на **один мажор в год**, и следующий, v23, выйдет только около **июня 2027**. Если у вас в проде ещё v20, сейчас самое время спланировать переезд сразу на v22, а заодно перестроить годовой план обновлений под новый ритм.

**Что меняется.** До v22 Angular жил по схеме «мажор каждые 6 месяцев, 18 месяцев поддержки» (6 — active, 12 — LTS). С v22 схема другая: **мажор раз в 12 месяцев, поддержка 24 месяца** (12 active + 12 LTS), между мажорами 4–6 минорных релизов примерно каждые 8 недель. Breaking changes — только в мажорах, миноры несут новые фичи без поломок. Официальная таблица на [angular.dev](https://angular.dev/reference/releases) сейчас выглядит так:

| Версия | Статус | Вышла | Active до | LTS до |
|---|---|---|---|---|
| 22 | active | 03.06.2026 | 06.2027 | 06.2028 |
| 21 | LTS | 19.11.2025 | 03.06.2026 | 06.2027 |
| 20 | LTS | 28.05.2025 | 19.11.2025 | **28.11.2026** |

То есть 28 ноября v20 становится тем же, чем был Node 20 весной: публично известные уязвимости дальше будут закрываться только в 21 и 22. Для внутреннего бэк-офиса это неприятно, для публичного SSR-приложения — уже риск, о котором спросит аудит или security-команда.

**Почему годовой цикл — не только хорошая новость.** Плюс очевиден: меньше обязательных апгрейдов, больше времени на фичи, понятный календарь (июнь — мажор). Минус тоньше: в один мажор теперь собирается год deprecation-ов вместо полугода, и откладывать обновление «на потом» стало дороже, потому что «потом» — это сразу большой скачок. Плюс миноры каждые 8 недель приносят новые API (а иногда и новые deprecation-предупреждения), и команда, которая игнорирует миноры, в июне получает и то, и другое разом. Отсюда практическое правило: **миноры — регулярно и мелко, мажор — по плану раз в год**.

**Как переехать с 20 на 22.** `ng update` рассчитан на шаг в один мажор: миграции (schematics) каждой версии пишутся относительно предыдущей. Поэтому дорога 20 → 21 → 22, с прогоном тестов между шагами, и ориентир — [Angular Update Guide](https://angular.dev/update-guide).

```bash
# шаг 1: 20 → 21 (отдельный PR, зелёный CI)
npx ng update @angular/core@21 @angular/cli@21
npx ng update @angular/material@21   # если есть, тем же шагом
npm test && npx ng build

# шаг 2: 21 → 22 (второй PR)
npx ng update @angular/core@22 @angular/cli@22
npx ng update @angular/material@22
```

```jsonc
// renovate.json — миноры и патчи Angular одной группой, мажор вручную
{
  "packageRules": [
    {
      "matchPackageNames": ["@angular/**", "@angular-devkit/**"],
      "groupName": "angular",
      "matchUpdateTypes": ["minor", "patch"]
    },
    {
      "matchPackageNames": ["@angular/**"],
      "matchUpdateTypes": ["major"],
      "enabled": false
    }
  ]
}
```

Перед стартом проверьте сторонние библиотеки: чаще всего обновление тормозит не сам Angular, а UI-кит, NgRx, библиотека графиков или внутренний пакет другой команды, у которых ещё нет версии под 22. Это и есть критический путь, а не ваш код.

**Зачем это тимлиду:** дедлайн поддержки — редкий случай, когда техническую задачу легко «продать»: дата, риск (нет security-патчей) и объём работы понятны заранее (мы обсуждали это вчера в уроке про tech debt). А годовой цикл позволяет один раз закрепить ритм в роадмапе: **июнь–июль — окно мажорного апгрейда**, миноры — в обычном потоке зависимостей через бота. Такой ритм легче защищать, чем разовые «у нас тут срочный апгрейд».

**Применить завтра:**

- Пройдитесь по всем репозиториям команды и выпишите версию `@angular/core`. Всё, что на 20 и ниже, — задача с дедлайном 28.11 (или осознанное, записанное решение принять риск до конкретной даты).
- Внесите в роадмап на 2027 год «окно апгрейда Angular 23» в июне–июле и настройте бота так, чтобы миноры приходили одной группой.
