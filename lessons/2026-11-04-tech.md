# 💻 День 21 · 2026-11-04 · backend: REST vs GraphQL vs tRPC — компромиссы

**Коротко:** все три подхода решают одну задачу — договориться фронту и бэку о данных, — но платят за это в разных местах. REST платит количеством запросов и ручной синхронизацией типов, GraphQL — сложностью сервера, кеша и безопасности, tRPC — жёсткой связкой с TypeScript и одним репозиторием. Выбор определяют не «модность», а **кто клиенты API** и **как устроены команды**.

**Что на самом деле сравниваем.** Удобно смотреть на три оси: *контракт* (где живёт описание API и как типы попадают на фронт), *форма данных* (кто решает, какие поля придут) и *инфраструктура* (кеш, наблюдаемость, безопасность). **REST** — ресурсы и HTTP-семантика: `GET /orders/42`, коды статусов, `ETag`, `Cache-Control`. Контракт — OpenAPI, клиент на Angular генерируется (`ng-openapi-gen`, `orval`, `openapi-generator`). HTTP-кеш, CDN, логи по URL и rate limiting работают «из коробки». Цена — over/under-fetching: экран заказа делает три запроса или получает DTO на 40 полей, из которых нужны 6. Обычно это лечат BFF или эндпоинтами «под экран». **GraphQL** — одна точка входа и схема с типами; клиент сам описывает, какие поля нужны. Это убирает лишние запросы и даёт сильную типизацию через codegen. Но сложность переезжает на сервер: каждый резолвер — потенциальный N+1 к базе (нужен DataLoader), запросы идут `POST` на один URL, и HTTP-кеш с CDN почти бесполезны без persisted queries, а произвольный глубокий запрос — это DoS-вектор, нужны лимиты глубины и стоимости. **tRPC** — вообще не протокол, а RPC-функции на TypeScript: сервер описывает процедуры, клиент импортирует **тип** роутера, и автокомплит с проверкой типов работает без схемы и кодогенерации. Переименовал поле на бэке — фронт не компилируется. Цена: и сервер, и клиент обязаны быть на TypeScript и видеть общие типы (обычно монорепо), а внешним потребителям, мобильным клиентам на Swift/Kotlin и партнёрам такое API почти бесполезно.

**Правило выбора, которое работает.** Публичное API или много разных клиентов (мобилки, партнёры, другие языки) — **REST + OpenAPI**, иногда GraphQL. Внутренний фронт и бэк в одном Nx-монорепо, один язык, одна команда — **tRPC** даёт максимум скорости; хороший компромисс — **REST с контрактом, сгенерированным из кода** (Zod/class-validator → OpenAPI → Angular-клиент). Много доменов и команд, сложные связанные данные, десятки экранов, которые собирают их по-разному, — **GraphQL** (часто как федерация поверх сервисов), но только если есть кому его эксплуатировать. В Angular важна ещё одна деталь: у tRPC нет официального Angular-адаптера (официальные интеграции — React Query и vanilla-клиент), поэтому его оборачивают в свой сервис поверх `@trpc/client` и отдают наружу Observable или `resource`. У GraphQL есть зрелый `apollo-angular`, у REST — обычный `HttpClient` и `httpResource`.

```ts
// tRPC: сервер (Node/NestJS-адаптер или standalone)
export const appRouter = router({
  orderById: publicProcedure
    .input(z.object({ id: z.string() }))
    .query(({ input }) => db.order.findUnique({ where: { id: input.id } })),
});
export type AppRouter = typeof appRouter; // экспортируем ТОЛЬКО тип

// Angular: тонкая обёртка над vanilla-клиентом
@Injectable({ providedIn: 'root' })
export class Api {
  private client = createTRPCClient<AppRouter>({
    links: [httpBatchLink({ url: '/trpc' })],
  });
  orderById(id: string) {
    return from(this.client.orderById.query({ id })); // тип ответа выведен с сервера
  }
}
```

**Типичные ошибки команд.** (1) GraphQL «для гибкости» на проекте с одним фронтом и одним бэком: получают все издержки и почти никаких выгод. (2) REST без OpenAPI: типы на фронте пишутся руками и тихо расходятся с бэком — это лечится не сменой протокола, а генерацией клиента в CI. (3) tRPC, который потом надо отдать мобильной команде: приходится строить REST рядом. (4) Сравнение по бенчмаркам размера ответа — на практике разница теряется на фоне базы и сети.

**Зачем это тимлиду:** выбор API-стиля — это решение об организации, а не о синтаксисе. Он определяет, сколько ручной синхронизации будет между фронтом и бэком, кто владеет контрактом и как быстро команда заметит ломающее изменение. Хороший тимлид ставит вопрос не «что лучше», а «где у нас реально болит»: лишние запросы, рассинхрон типов или скорость изменений.

**Применить завтра:**

- Найди в проекте 3 места, где типы ответа API написаны на фронте руками. Если такие есть, поставь в CI генерацию Angular-клиента из OpenAPI и проверку `git diff`: ломающее изменение на бэке станет красной сборкой, а не багом в проде.
- Если предлагают GraphQL или tRPC, попроси короткий ADR с ответами на три вопроса: кто клиенты API через год, как будем кешировать и что делаем с N+1 / доступом для не-TS клиентов.
