# 💻 День 35 · 2026-11-18 · backend: PostgreSQL — индексы, EXPLAIN и N+1

**Коротко:** почти все «бэкенд тормозит» в продуктовой команде сводятся к трём вещам: нет нужного индекса (или он есть, но не в том порядке колонок), запрос никто не смотрел через `EXPLAIN`, и ORM тихо делает N+1. Разберём, как это читать и ловить до продакшна, и что из этого тимлид фронтенда должен требовать на ревью BFF и NestJS-кода.

**Индексы: нюансы, на которых ошибаются.** B-tree — дерево, отсортированное по колонкам индекса **в заданном порядке**. Поэтому составной индекс `(tenant_id, status, created_at)` идеально обслуживает `WHERE tenant_id = $1 AND status = 'open' ORDER BY created_at DESC`, но для фильтра по одному `created_at` почти бесполезен. Правило: сначала колонки с равенством, потом диапазон или сортировка. В PostgreSQL 18 (релиз сентября 2025) появился **skip scan**: планировщик умеет использовать составной индекс, даже если в запросе нет условия на первую колонку, но выигрыш есть только когда у первой колонки мало разных значений (`status`, `tenant_id` в маленьком SaaS). Это страховка, а не повод не думать о порядке. Ещё три вещи, которые часто забывают. (1) Postgres **не создаёт индекс на внешний ключ** автоматически, только на `PRIMARY KEY` и `UNIQUE`: `order_items.order_id` без индекса — это seq scan на каждый join и медленное удаление заказа. (2) **Частичный индекс** `WHERE deleted_at IS NULL` меньше и быстрее, если почти все запросы идут по «живым» строкам. (3) **Покрывающий индекс** `INCLUDE (total)` даёт Index Only Scan без похода в таблицу, но только если таблицу регулярно чистит `VACUUM` (иначе в плане будут `Heap Fetches`). Цена каждого индекса — медленнее запись и больше места, поэтому «проиндексируем всё» — тоже ошибка.

**EXPLAIN: что реально читать.** `EXPLAIN` показывает план с **оценками**, `EXPLAIN ANALYZE` **выполняет** запрос и показывает факт. Для `UPDATE`/`DELETE` это значит, что данные реально изменятся, поэтому оборачивай в `BEGIN; … ROLLBACK;`. С PostgreSQL 18 `EXPLAIN ANALYZE` по умолчанию выводит и `BUFFERS` (сколько страниц прочитано из кеша и с диска), а для индексных сканов показывает `Index Searches`. Читать план стоит снизу вверх и смотреть на четыре вещи: тип узла (`Seq Scan` на большой таблице — подозрение), расхождение `rows` оценочных и `actual rows` (в 10–100 раз — устаревшая статистика, нужен `ANALYZE` или расширенная статистика), `loops` (узел, выполненный 5000 раз, — это N+1 внутри базы, обычно Nested Loop без индекса) и `Buffers: shared read` (чтение с диска, а не из памяти).

**N+1.** Классика ORM: загрузили 50 заказов одним запросом, а потом в цикле для каждого лениво подтянули покупателя — 51 запрос. Каждый быстрый (1–2 мс), поэтому в `EXPLAIN` ничего страшного не видно, а эндпоинт отвечает 300 мс из-за сетевых round-trip'ов и пула соединений. То же самое бывает на фронте: компонент строки таблицы сам вызывает `GET /customers/:id`, и список из 50 строк — это 51 HTTP-запрос. Лечится одинаково: **собрать ID и взять одним запросом** (`JOIN`, `WHERE id = ANY($1)`, `include` в Prisma, `relations` в TypeORM, DataLoader в GraphQL), а на фронте — отдать списку уже агрегированные данные из BFF.

```ts
// ❌ N+1: 1 запрос за заказами + по запросу на каждого покупателя
const orders = await db.order.findMany({ where: { tenantId }, take: 50 });
for (const o of orders) {
  o.customer = await db.customer.findUnique({ where: { id: o.customerId } });
}

// ✅ Два запроса независимо от размера страницы
const orders = await db.order.findMany({ where: { tenantId }, take: 50 });
const ids = [...new Set(orders.map(o => o.customerId))];
const customers = await db.customer.findMany({ where: { id: { in: ids } } });
const byId = new Map(customers.map(c => [c.id, c]));
const result = orders.map(o => ({ ...o, customer: byId.get(o.customerId) }));

// ✅ Или один запрос с join (ORM сделает его сам)
const ordersWithCustomer = await db.order.findMany({
  where: { tenantId }, take: 50, include: { customer: true },
});
```

```sql
-- Индекс под конкретный запрос списка: равенства → сортировка, плюс покрытие
CREATE INDEX CONCURRENTLY idx_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC)
  INCLUDE (total)
  WHERE deleted_at IS NULL;

-- Проверяем план (в PG 18 BUFFERS включён по умолчанию)
EXPLAIN ANALYZE
SELECT id, total, created_at FROM orders
WHERE tenant_id = 42 AND status = 'open' AND deleted_at IS NULL
ORDER BY created_at DESC LIMIT 50;
-- Хорошо: Index Only Scan using idx_orders_tenant_status_created
--         actual rows=50 loops=1, Heap Fetches: 0, Buffers: shared hit=5
-- Плохо:  Seq Scan on orders … Rows Removed by Filter: 1 200 000
```

Важная деталь в миграции: `CREATE INDEX CONCURRENTLY` не блокирует запись в таблицу, но **не работает внутри транзакции**, а большинство миграторов (Prisma, TypeORM, Flyway) по умолчанию заворачивают миграцию в транзакцию. Обычный `CREATE INDEX` на таблице в миллионы строк блокирует `INSERT`/`UPDATE` на минуты, и это выглядит как «прод лёг на деплое».

**Как ловить системно.** Расширение `pg_stat_statements` собирает статистику по нормализованным запросам: сортировка по `total_exec_time` показывает, что реально ест базу, а огромное `calls` у простого `SELECT … WHERE id = $1` — почти всегда N+1. `auto_explain` пишет в лог планы запросов дольше порога. В интеграционных тестах можно считать запросы на эндпоинт: тест «список заказов делает не больше 3 запросов» ловит N+1 ещё на PR.

**Зачем это тимлиду:** фронтенд-команда с BFF или NestJS пишет SQL через ORM и не видит, что под капотом. Медленный список в UI почти никогда не лечится виртуальным скроллом, если бэкенд отвечает секунду. Тимлиду не нужно быть DBA, но нужно уметь задать на ревью три вопроса: «какой индекс обслуживает этот запрос?», «где план?» и «сколько запросов делает этот эндпоинт на странице из 50 строк?». И знать, какая миграция может положить прод.

**Применить завтра:**

- Добавь в чек-лист PR для BFF/бэкенда: новый запрос к большой таблице — с выводом `EXPLAIN ANALYZE` в описании; новый внешний ключ — с индексом; индекс на живой таблице — только `CONCURRENTLY` в отдельной нетранзакционной миграции.
- Попроси доступ к `pg_stat_statements` на стейдже или проде и посмотри топ-10 по `total_exec_time` и по `calls`: за полчаса обычно находится хотя бы один N+1 и один запрос без индекса.
