# 💻 День 6 · 2026-10-20 · backend: Node.js event loop глубже — microtasks, libuv

**Коротко:** event loop в Node.js — это не «одна очередь колбэков», а цикл фаз libuv, между которыми Node.js каждый раз досуха выгребает две свои очереди: `process.nextTick` и микрозадачи промисов. Порядок этих очередей объясняет почти все «странные» баги: от недетерминированного `setTimeout` против `setImmediate` до зависшего сервера, у которого CPU не загружен.

**Фазы libuv.** Одна итерация цикла проходит фазы: **timers** (`setTimeout`/`setInterval`, чей срок истёк) → **pending callbacks** (отложенные системные колбэки, например часть ошибок TCP) → idle/prepare (внутренние) → **poll** (ждём и обрабатываем I/O: сокеты, файлы) → **check** (`setImmediate`) → **close callbacks** (`'close'` у сокетов). Нюанс, о котором мало кто знает: начиная с libuv 1.45.0 (Node.js 20) таймеры выполняются *после* фазы poll, а не до неё; для обратной совместимости libuv один раз прогоняет таймеры перед входом в цикл. Отсюда классика: `setTimeout(fn, 0)` против `setImmediate(fn)` в главном модуле дают недетерминированный порядок (зависит от того, успела ли пройти 1 мс), а внутри I/O-колбэка `setImmediate` всегда первый — check идёт сразу после poll.

**Микрозадачи и nextTick.** После *каждого* колбэка из любой фазы Node.js сначала опустошает очередь `process.nextTick`, затем очередь микрозадач (`.then`, `await`, `queueMicrotask`), и так пока обе не пусты. Это значит, что рекурсивный `nextTick` или бесконечная цепочка промисов не дадут циклу дойти до poll: I/O «голодает», запросы висят, хотя процесс жив. Второй нюанс: в CommonJS `nextTick` всегда раньше `queueMicrotask`, а в ES-модулях наоборот — сам модуль уже исполняется внутри микрозадачи. Поэтому код, полагающийся на порядок `nextTick` и промисов, может молча поменять поведение при переходе на ESM. В документации Node.js `process.nextTick` теперь помечен как **Legacy** (с v22.7.0 / v20.18.0) с рекомендацией использовать `queueMicrotask()`.

**Thread pool libuv.** Сетевой I/O в Node.js по-настоящему неблокирующий (epoll/kqueue/IOCP), а вот файловая система, `dns.lookup`, часть `crypto` (`pbkdf2`, `scrypt`, `randomBytes`) и `zlib` уходят в пул потоков libuv — по умолчанию **4 потока** (`UV_THREADPOOL_SIZE`, максимум 1024). Пять параллельных `crypto.pbkdf2` на 4 потоках — и пятый ждёт; добавьте к этому медленный NFS и `dns.lookup`, и логин «тормозит» без всякой нагрузки на event loop. Пул — это не про ваш JS: тяжёлые вычисления в JS по-прежнему блокируют главный поток, для них нужны `worker_threads`.

```ts
// main.mjs (ESM). Угадайте порядок до запуска.
import { readFile } from 'node:fs';

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
queueMicrotask(() => console.log('microtask'));

readFile(import.meta.filename, () => {
  setTimeout(() => console.log('io → timeout'), 0);
  setImmediate(() => console.log('io → immediate')); // всегда раньше io → timeout
});

// В ESM: microtask, nextTick, затем timeout/immediate в любом порядке,
// внутри I/O: io → immediate, io → timeout.
// Переименуйте в .cjs (и замените import.meta.filename на __filename):
// nextTick окажется раньше microtask.
```

```ts
// Детектор «голодания» event loop: дешевле, чем гадать по логам
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  const p99 = h.percentile(99) / 1e6; // нс → мс
  if (p99 > 100) console.warn(`event loop lag p99=${p99.toFixed(1)}ms`);
  h.reset();
}, 10_000).unref();
```

**Зачем это тимлиду:** фронтенд-команды всё чаще владеют Node.js-кодом — SSR в Angular, BFF, тулинг, CI-скрипты. Медленный SSR, «рандомные» таймауты и флакающие тесты на таймерах часто объясняются не нагрузкой, а этими механиками: синхронная сериализация большого JSON в SSR, рекурсивные микрозадачи, `bcrypt`/`pbkdf2` в пуле из 4 потоков. Понимая фазы, вы на ревью сразу видите, где код зависит от порядка выполнения, и задаёте правильные вопросы на инцидент-разборе: «лаг event loop или очередь в пуле?».

**Применить завтра:**

- Добавьте в SSR/BFF-сервис метрику event loop lag (`monitorEventLoopDelay` или `performance.eventLoopUtilization()`) рядом с латентностью запросов — это первый график, который нужен на инциденте «всё тормозит».
- На ревью ищите `process.nextTick` в новом коде и тесты, завязанные на порядок `setTimeout(0)`/`setImmediate`/промисов: заменяйте на `queueMicrotask`, fake timers или явное ожидание результата.
