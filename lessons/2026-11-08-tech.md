# 💻 День 25 · 2026-11-08 · news: Node.js анонсировал security-релиз на 11 ноября — плейбук для команды

**Коротко:** 4 ноября проект Node.js разослал **pre-alert**: «на или вскоре после 11 ноября 2026» выйдут security-релизы для линий **22, 24 и 26**, самая серьёзная уязвимость — уровня **HIGH**. Деталей и CVE пока нет, они появятся в день релиза. У команды есть три дня, чтобы подготовиться, и это хороший повод один раз завести плейбук «как мы катим патчи рантайма», а не устраивать пожар каждый раз.

**Что случилось.** Node.js публикует security-релизы по предсказуемой схеме: примерно за неделю — pre-alert в рассылке [nodejs-sec / oss-security](https://www.openwall.com/lists/oss-security/2026/11/04/3) и на странице [advisory](https://nodejs.org/en/blog/vulnerability/november-2026-security-releases): какие линии, максимальная серьёзность, ориентировочная дата. Подробности (что за баг, CVE, исправленные версии) раскрываются **только в день релиза**, одновременно с патчем: так атакующие не получают фору. Это уже второй security-релиз за месяц: предыдущий вышел 21 октября для тех же трёх линий.

Ключевая фраза из таких анонсов, которую стоит повесить над столом: **EOL-версии тоже уязвимы, но патча для них не будет**. Node 20 закончил поддержку в апреле 2026 — если он остался в каком-то CI-раннере, в базовом образе SSR-сервиса или в забытой serverless-функции, 11 ноября вы получите публично описанную HIGH-уязвимость без возможности её закрыть мелким апдейтом. Только переездом на поддерживаемую линию.

**Насколько это касается фронтенда.** Риск зависит от того, **где** у вас крутится Node:

- **Angular SSR / прокси / BFF в проде** — Node принимает трафик из интернета. Самые серьёзные уязвимости Node исторически сидят как раз в HTTP-парсере, TLS и обработке заголовков. Это первый приоритет: патчим в день-два.
- **CI и сборка** — Node выполняет ваши зависимости и скрипты, но наружу не слушает. Риск ниже, но раннеры часто имеют доступ к секретам и npm-токенам. Обновляем в течение недели.
- **Локальные машины разработчиков** — обновляются вместе с `.nvmrc` через обычный PR.
- **SPA без SSR** — в браузер Node не попадает, итоговый бандл уязвимость Node не наследует.

**Как подготовиться до 11-го.** Цель — чтобы в день релиза обновление было делом одного PR, а не расследованием.

```dockerfile
# Dockerfile SSR-сервиса: мажор + LTS-тег, а не точная версия навсегда.
# Пересборка без кеша подтянет свежий патч линии 24.
FROM node:24-bookworm-slim AS runtime
# если вы пиннитесь по digest (это правильно для воспроизводимости),
# то обновление digest должен делать бот — Renovate или Dependabot
```

```yaml
# .github/workflows/ci.yml — берём свежий патч линии, а не закешированный
- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc   # в .nvmrc: 24 (или 26)
    check-latest: true          # без этого раннер может взять старый кеш
```

```ts
// scripts/check-node.ts — защита от «забытого» Node в CI и SSR-контейнере
const [major] = process.versions.node.split('.').map(Number);
const supported = [22, 24, 26];
if (!supported.includes(major)) {
  console.error(`Node ${process.versions.node} — EOL, патчей безопасности не будет`);
  process.exit(1);
}
```

**Зачем это тимлиду:** security-патч рантайма — классическая задача «ничья»: бэкенд думает, что это фронт (SSR же ваш), DevOps думает, что это команда приложения, а команда ждёт, что базовый образ обновится сам. Pre-alert даёт редкую роскошь — знать дату заранее. Используйте её, чтобы назначить владельца и договориться об SLA: например, **HIGH/CRITICAL в интернет-сервисах — 48 часов, CI — неделя, остальное — обычный цикл зависимостей**. Записанное правило снимает спор «а надо ли сейчас» с каждого следующего релиза.

**Применить завтра:**

- Проведите 15-минутную инвентаризацию: где у вас Node (Dockerfile, `FROM node:`, CI-раннеры, Lambda/Cloud Functions, `.nvmrc`), какие версии и кто владелец. Всё, что на 20 и ниже, — отдельная срочная задача.
- Назначьте на 11–12 ноября дежурного: прочитать advisory, оценить, затрагивает ли уязвимость ваш сценарий (например, только HTTP/2 или только определённый API), и выкатить обновлённый образ SSR. Запишите SLA по серьёзности в README команды.
