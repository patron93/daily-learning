# 💻 День 12 · 2026-10-26 · architecture: микрофронтенды, Module и Native Federation и когда оно того не стоит

**Коротко:** микрофронтенды решают организационную проблему (много команд мешают друг другу релизить), а не техническую. В Angular сегодня стандарт де-факто — Native Federation: те же идеи, что у Module Federation, но на ES-модулях и import maps, без webpack. Платите вы за это сложностью рантайма, версий и UX, поэтому сначала стоит доказать, что модульный монолит не справляется.

**Что это на самом деле.** Микрофронтенд — это кусок UI, который команда собирает и **деплоит независимо**, а shell (host) подтягивает его в рантайме. Ключевое слово «деплоит»: если все части всё равно выкатываются одним релизом, у вас не микрофронтенды, а распределённый монолит с худшими свойствами обоих миров. Module Federation (webpack 5, а теперь Module Federation 2.0 с отдельным рантаймом, манифестом и поддержкой Rspack/Vite) ввёл модель: remote объявляет `exposes`, host знает, где лежит remote, а общие зависимости (`shared`) договариваются о версиях в рантайме, чтобы Angular грузился один раз.

**Почему в Angular — Native Federation.** С Angular 17 CLI собирает через esbuild (`application` builder), а классический Module Federation завязан на рантайм webpack/Rspack, то есть на кастомные билдеры. Native Federation от Manfred Steyer (angular-architects) переносит ту же ментальную модель на стандарты браузера: remote при сборке публикует `remoteEntry.json` (что он отдаёт и какие shared-пакеты с какими версиями несёт), shell по `federation.manifest.json` собирает из них общий **import map**, а загрузка remote — это обычный динамический `import()`. Shared-зависимости собираются отдельными бандлами, так что `@angular/core` разрешается в один URL для всех. Для браузеров без нужной поддержки работает полифилл `es-module-shims`.

**Актуальное состояние (проверено на октябрь 2026).** Native Federation переехал из репозитория `angular-architects/module-federation-plugin` в отдельную организацию `native-federation` и разделён на core, orchestrator и Angular-адаптер (v4, весь на ESM, конфиг `federation.config.mjs`). В плагине 22.0.0 (сентябрь 2026) Native Federation из старого репозитория убрали, v3 остаётся только на патчах. Для Angular 22+ пакет снова называется `@angular-architects/native-federation`, для Angular 20–21 есть `@angular-architects/native-federation-v4`; мажор адаптера держите равным мажору CLI. Полезные фичи последних версий: `ignoreUnusedDeps` (делит только реально используемые пакеты вместо всего `package.json`), автоматическое разбиение shared-пакетов на чанки, поддержка SSR с hydration и i18n, а также совместная работа с Module Federation для поэтапной миграции.

```js
// remote: federation.config.mjs (схематично, v4)
import { withNativeFederation, shareAll } from '@angular-architects/native-federation/config';

export default withNativeFederation({
  name: 'checkout',
  exposes: { './routes': './src/app/checkout.routes.ts' }, // отдаём роуты, а не компонент: границу держит роутер
  shared: {
    ...shareAll({ singleton: true, strictVersion: true, requiredVersion: 'auto' }),
  },
  features: { ignoreUnusedDeps: true },
});
```

```ts
// shell: app.routes.ts
export const routes: Routes = [
  {
    path: 'checkout',
    loadChildren: () => loadRemoteModule('checkout', './routes').then(m => m.CHECKOUT_ROUTES),
  },
];
```

**Когда оно того не стоит.** Главные скрытые издержки: (1) **версии shared** — один remote обновил Angular раньше других, и `strictVersion` либо роняет загрузку, либо (без него) вы ловите две копии фреймворка и сломанный DI; на практике командам всё равно приходится обновлять мажор Angular синхронно. (2) **Контракты в рантайме** — тип `exposes` не проверяется при сборке shell, ошибка всплывёт у пользователя; нужны контрактные и e2e-тесты на интеграцию. (3) **Глобальное состояние и UX** — общий стор, тема, i18n и дизайн-система превращаются в распределённый API, а консистентность интерфейса держится на дисциплине. (4) **Операционка** — CDN, кеширование `remoteEntry.json`, откат одного remote, локальная разработка с пятью дев-серверами. Если у вас одна-две команды, общий релизный цикл или проблема на самом деле в медленном CI, лучше модульный монолит в Nx с тегами и `enforce-module-boundaries` (урок 18 октября) плюс `nx affected`: он даёт 80% выгоды без рантайм-рисков. Хороший сигнал «пора»: несколько автономных команд, разный темп релизов, чётко отделимые по роутам домены, а иногда и легаси, которое нужно постепенно заменить (strangler pattern).

**Зачем это тимлиду:** решение о микрофронтендах почти необратимо и на годы задаёт структуру команд (закон Конвея работает в обе стороны). Ваша задача — не дать архитектуре вырасти из моды или из желания «как у Spotify», а связать её с реальной болью: кто кого блокирует на релизе и сколько это стоит. И если решаетесь — заранее закрепить правила: синхронный апдейт Angular, роуты как граница, дизайн-система как отдельный версионируемый пакет, никакого общего мутабельного стора между remotes.

**Применить завтра:**

- Посчитайте за последний квартал, сколько релизов задержались из-за чужой команды или общего регресса. Если почти ни одного — фиксируйте в ADR, что микрофронтенды пока не нужны, и почему.
- Если они уже есть: проверьте, включён ли `ignoreUnusedDeps` и совпадают ли мажоры Angular во всех remotes. Расхождение — первый кандидат на продовый инцидент.
