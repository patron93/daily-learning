# 💻 День 8 · 2026-10-22 · classic: SOLID в Angular подробно: good vs bad

**Коротко:** вчера был словарь SOLID, сегодня практика ревью. По каждому принципу — нюанс, который обычно упускают, пара ❌ Плохо / ✅ Хорошо из типичного Angular-кода (компоненты, интерцепторы, формы, DI, тесты) и честный абзац о том, где принцип перегибают. Читается 10–12 минут.

Контекст версии: в Angular v22 (июнь 2026) OnPush стал стратегией по умолчанию для новых приложений, Signal Forms вышли в stable, а для root-сервисов рекомендован декоратор `@Service()` вместо `@Injectable({ providedIn: 'root' })`. Примеры ниже написаны так, что работают и на v20–v21; где это важно, разница отмечена.

## S — Single Responsibility: режем по акторам, а не по строчкам

**Нюанс.** SRP не означает «маленький файл». Вопрос один: сколько разных людей (ролей) придут менять этот код. Если бэкенд меняет формат ответа, продукт — правила фильтрации, а дизайнер — вид таблицы, и всё это один файл, то каждый PR задевает чужую логику, а тест на фильтр ломается от правки вёрстки.

**❌ Плохо: интерцептор «на все случаи».**

```ts
export const appInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const toast = inject(ToastService);
  const started = performance.now();

  const authed = req.url.startsWith('/api')
    ? req.clone({ setHeaders: { Authorization: `Bearer ${auth.token()}` } })
    : req;

  return next(authed).pipe(
    retry({ count: req.method === 'GET' ? 2 : 0, delay: 500 }),
    tap(() => console.log(req.url, performance.now() - started)),
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) auth.logout();
      else toast.error('Что-то пошло не так');
      return throwError(() => err);
    }),
  );
};
```

Здесь пять причин для изменения: схема авторизации (security), политика ретраев (SRE), метрики (observability), UX ошибок (продукт) и обработка 401 (auth-флоу). Тонкий баг: ретрай стоит *до* `catchError`, и при 503 пользователь ждёт три запроса, прежде чем увидит тост, а отключить ретрай для одного запроса нельзя.

**✅ Хорошо: цепочка маленьких интерцепторов с явным порядком.**

```ts
export const SKIP_RETRY = new HttpContextToken<boolean>(() => false);

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (!req.url.startsWith('/api')) return next(req);
  const token = inject(AuthService).token();
  return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }));
};

export const retryInterceptor: HttpInterceptorFn = (req, next) =>
  req.method !== 'GET' || req.context.get(SKIP_RETRY)
    ? next(req)
    : next(req).pipe(retry({ count: 2, delay: 500 }));

export const errorToastInterceptor: HttpInterceptorFn = (req, next) => {
  const toast = inject(ToastService);
  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status !== 401) toast.error(messageFor(err));
      return throwError(() => err);
    }),
  );
};

// app.config.ts — порядок важен: запрос идёт сверху вниз, ответ снизу вверх
provideHttpClient(
  withInterceptors([authInterceptor, errorToastInterceptor, retryInterceptor, timingInterceptor]),
);
```

Почему лучше: каждый интерцептор тестируется отдельно (`TestBed` + `HttpTestingController` с одним интерцептором), порядок виден в одном месте, а исключения делаются через `HttpContextToken`, без флагов в URL. Тост стоит выше ретрая, поэтому срабатывает один раз, на финальной ошибке.

**❌ Плохо: «умный» компонент-страница.** `OrdersPageComponent` сам делает `http.get`, держит фильтры в полях, синхронизирует их с `queryParams`, считает итоги и форматирует суммы в шаблоне через методы. Типичный симптом — `ngOnInit` на 60 строк и тест, которому для проверки итоговой суммы нужен `RouterTestingHarness`.

**✅ Хорошо:** `OrdersStore` (сигналы + `httpResource`/сервис данных: серверное состояние), фильтры как `input()` из роутера через `withComponentInputBinding()` (URL-состояние), `OrdersTable` с `input()`/`output()` (только отображение), pipe `money` (форматирование). Итоги — `computed` в store, и тестируются они без DOM.

**Где перегибают.** Компонент на 40 строк с одним запросом и одной таблицей не нужно резать на facade + store + data-service + presentational. Если все части меняет одна роль и одновременно, разрез только добавляет файлов и прыжков по IDE. Сигнал к разрезу — второй актор или второй потребитель, а не число строк.

## O — Open/Closed: точки расширения, а не растущий `@switch`

**Нюанс.** OCP не требует, чтобы код «никогда не менялся». Он требует, чтобы *типовое* изменение (новый тип колонки, новый способ оплаты, новый виджет) делалось добавлением, а не правкой ядра. Значит, сначала надо понять, по какой оси система реально растёт, и открыть именно её.

**❌ Плохо: таблица, которая знает обо всех типах ячеек.**

```html
<!-- data-table.component.html -->
@for (col of columns(); track col.key) {
  <td>
    @switch (col.type) {
      @case ('money') { {{ row[col.key] | currency: 'PLN' }} }
      @case ('status') { <app-status-chip [status]="row[col.key]" /> }
      @case ('user') { <app-avatar [userId]="row[col.key]" /> }
      @case ('actions') { <button (click)="edit.emit(row)">Edit</button> }
      @default { {{ row[col.key] }} }
    }
  </td>
}
```

Каждая фича дописывает сюда `@case`, общий компонент из ui-библиотеки начинает импортировать доменные компоненты (`app-status-chip` из orders, `app-avatar` из users), и граница библиотек в монорепо ломается.

**✅ Хорошо: шаблон ячейки приходит снаружи.**

```ts
@Directive({ selector: 'ng-template[appCell]' })
export class CellDef {
  readonly column = input.required<string>({ alias: 'appCell' });
  readonly template = inject(TemplateRef);
}

@Component({
  selector: 'app-data-table',
  imports: [NgTemplateOutlet],
  template: `
    @for (row of rows(); track trackBy()(row)) {
      <tr>
        @for (col of columns(); track col) {
          <td>
            @if (cellFor(col); as tpl) {
              <ng-container *ngTemplateOutlet="tpl; context: { $implicit: row }" />
            } @else {
              {{ row[col] }}
            }
          </td>
        }
      </tr>
    }
  `,
})
export class DataTable<T extends Record<string, unknown>> {
  readonly rows = input.required<readonly T[]>();
  readonly columns = input.required<readonly string[]>();
  readonly trackBy = input<(row: T) => unknown>((row) => row);

  private readonly cells = contentChildren(CellDef);
  private readonly cellMap = computed(
    () => new Map(this.cells().map((c) => [c.column(), c.template])),
  );
  protected cellFor(col: string) {
    return this.cellMap().get(col) ?? null;
  }
}
```

```html
<!-- orders-page.component.html: доменная конкретика живёт в фиче -->
<app-data-table [rows]="store.orders()" [columns]="['id', 'total', 'status']">
  <ng-template appCell="total" let-order>{{ order.total | currency: 'PLN' }}</ng-template>
  <ng-template appCell="status" let-order><app-status-chip [status]="order.status" /></ng-template>
</app-data-table>
```

Почему лучше: таблица закрыта для изменений (её не трогают при новой колонке) и открыта для расширения (любой шаблон). Ui-библиотека не зависит от доменных фич, и правило `enforce-module-boundaries` проходит.

**Где перегибают.** «Сделаем конфигурируемым всё»: таблица на 30 input-ов, JSON-схема колонок, плагины для сортировки, хотя таблица используется в двух местах. Точку расширения стоит открывать, когда по этой оси прошло хотя бы второе-третье изменение. До этого `@switch` на три случая честнее и проще читается.

## L — Liskov: соблюдай контракт, который не написан в типах

**Нюанс.** TypeScript проверяет сигнатуры, но не поведение. LSP нарушается там, где реализация формально подходит по типу, но ведёт себя иначе, чем ждёт потребитель: вызывает колбэки не тогда, бросает исключение там, где контракт обещает «тихо», меняет синхронность. В Angular самый частый случай — `ControlValueAccessor`: Forms API — это потребитель, и у него жёсткий контракт.

**❌ Плохо: свой контрол, который формально реализует CVA.**

```ts
@Component({
  selector: 'app-rating',
  providers: [{ provide: NG_VALUE_ACCESSOR, useExisting: Rating, multi: true }],
  template: `@for (s of stars; track s) {
    <button type="button" (click)="select(s)">★</button>
  }`,
})
export class Rating implements ControlValueAccessor {
  stars = [1, 2, 3, 4, 5];
  value = 0;
  private onChange = (v: number) => {};

  writeValue(v: number) {
    this.value = v;
    this.onChange(v);          // ❌ эхо обратно в форму
  }
  registerOnChange(fn: (v: number) => void) { this.onChange = fn; }
  registerOnTouched() {}       // ❌ touched никогда не наступит
  select(s: number) { this.value = s; this.onChange(s); }
  // ❌ setDisabledState нет: form.disable() ничего не делает
}
```

Что ломается у потребителя: `form.patchValue()` вызывает `writeValue`, тот вызывает `onChange`, форма становится `dirty` без действий пользователя, и guard «есть несохранённые изменения» срабатывает сразу после загрузки. Ошибки валидации с `updateOn: 'blur'` или показом «после touched» никогда не появятся. `disable()` визуально не блокирует звёзды. Типы при этом зелёные.

**✅ Хорошо: контракт соблюдён полностью.**

```ts
export class Rating implements ControlValueAccessor {
  protected readonly value = signal(0);
  protected readonly disabled = signal(false);
  private onChange: (v: number) => void = () => {};
  private onTouched: () => void = () => {};

  writeValue(v: number | null) { this.value.set(v ?? 0); }   // модель → вид, без эха
  registerOnChange(fn: (v: number) => void) { this.onChange = fn; }
  registerOnTouched(fn: () => void) { this.onTouched = fn; }
  setDisabledState(d: boolean) { this.disabled.set(d); }

  select(s: number) {                                          // вид → модель
    if (this.disabled()) return;
    this.value.set(s);
    this.onChange(s);
    this.onTouched();
  }
}
```

Правило: `writeValue` — направление «модель → вид» и никогда не вызывает `onChange`; `onChange` — только в ответ на действие пользователя; `null` — легальное значение (так приходит `reset()`); disabled поддерживается. Ещё лучше — один общий тест-харнесс «CVA contract» для всех контролов дизайн-системы: подставляет контрол в `FormControl` и проверяет pristine после `patchValue`, touched после blur, `disable()`. Это и есть LSP как автоматическая проверка. (В Signal Forms контракт другой и проще, но идея та же: потребитель — форма, и она ждёт определённого поведения.)

**❌ Плохо, второй пример: подмена через наследование.** `class ReadonlyCart extends CartStore` с `override add() { throw new Error('readonly'); }`. Любой код, который принимает `CartStore`, теперь может упасть в рантайме. **✅ Хорошо:** выделить роль «только чтение» в отдельную абстракцию (см. I ниже) и отдавать её тем, кому запись не нужна.

**Где перегибают.** LSP не запрещает наследование и не требует писать формальные пред- и постусловия к каждому методу. Перегиб — отказываться от `extends` даже для базовых классов без поведения или писать абстрактный класс ради «подменяемости», которую никто не использует. Достаточно того, чтобы у публичной абстракции контракт (синхронность, ошибки, `null`, побочные эффекты) был описан в JSDoc и проверен тестом.

## I — Interface Segregation: роли через `useExisting`

**Нюанс.** ISP — это не только про размер интерфейса, но и про *связность изменений*: если 15 компонентов зависят от `CartStore` целиком, любой рефакторинг его записи требует перепроверить все 15, даже тех, кто только показывает число товаров. В Angular роль удобно выразить абстрактным классом-токеном и отдать одну реализацию под несколькими ролями.

**❌ Плохо: все инжектят полный store.**

```ts
@Component({ selector: 'app-cart-badge', template: `{{ cart.count() }}` })
export class CartBadge {
  protected readonly cart = inject(CartStore); // 25 методов, нужен один сигнал
}
```

Тест бейджа вынужден мокать `CartStore` целиком (или тащить настоящий с `HttpClient`), а ревьюер не видит по коду, что бейдж ничего не пишет.

**✅ Хорошо: узкие роли, одна реализация.**

```ts
export abstract class CartReader {
  abstract readonly items: Signal<readonly CartItem[]>;
  abstract readonly count: Signal<number>;
}
export abstract class CartWriter {
  abstract add(productId: string, qty?: number): void;
  abstract remove(productId: string): void;
}

@Injectable({ providedIn: 'root' }) // в v22 для таких сервисов рекомендован @Service()
export class CartStore implements CartReader, CartWriter {
  /* ... */
}

// app.config.ts — один экземпляр, две роли
providers: [
  { provide: CartReader, useExisting: CartStore },
  { provide: CartWriter, useExisting: CartStore },
];

export class CartBadge {
  protected readonly cart = inject(CartReader); // видно: только чтение
}
```

Нюанс, на котором спотыкаются: нужен именно `useExisting`, а не `useClass`. С `useClass: CartStore` каждая роль получит **свой** экземпляр, и бейдж не увидит товары, добавленные через `CartWriter`. Тест бейджа теперь — `{ provide: CartReader, useValue: { items: signal([]), count: signal(3) } }`, две строки.

**Где перегибают.** Разбивать каждый сервис на `IFooReader`/`IFooWriter`/`IFooAdmin` по умолчанию. Роли окупаются там, где много потребителей и они явно делятся на группы (store корзины, auth, feature flags). Для сервиса с двумя потребителями узкий интерфейс — лишний уровень косвенности.

## D — Dependency Inversion: глобалы и время — тоже зависимости

**Нюанс.** DIP в Angular обычно понимают как «инжекти сервисы через DI», и это уже есть. Реальные нарушения прячутся в *неявных* зависимостях: `new Date()`, `Date.now()`, `window`, `localStorage`, `navigator.onLine`, `environment.apiUrl`, импортированный напрямую. Высокоуровневая логика (истёк ли токен, показать ли баннер) жёстко привязана к низкоуровневой платформе, поэтому её не протестировать без `jasmine.clock()`/`vi.useFakeTimers()` и не запустить на SSR.

**❌ Плохо.**

```ts
import { environment } from '../environments/environment';

@Injectable({ providedIn: 'root' })
export class SessionService {
  private readonly http = inject(HttpClient);

  isExpired(token: Token) {
    return token.expiresAt < Date.now();                 // время из ниоткуда
  }
  refresh() {
    const rt = localStorage.getItem('refresh');          // падает на SSR
    return this.http.post(`${environment.apiUrl}/auth/refresh`, { rt }); // конфиг вшит в сборку
  }
}
```

**✅ Хорошо: абстракции с дефолтной реализацией.**

```ts
export interface Clock {
  now(): number;
}
export const CLOCK = new InjectionToken<Clock>('CLOCK', {
  providedIn: 'root',
  factory: () => ({ now: () => Date.now() }),
});

export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL');

export const TOKEN_STORAGE = new InjectionToken<Pick<Storage, 'getItem' | 'setItem'>>('TOKEN_STORAGE', {
  providedIn: 'root',
  factory: () =>
    isPlatformBrowser(inject(PLATFORM_ID)) ? localStorage : { getItem: () => null, setItem: () => {} },
});

@Injectable({ providedIn: 'root' })
export class SessionService {
  private readonly http = inject(HttpClient);
  private readonly clock = inject(CLOCK);
  private readonly storage = inject(TOKEN_STORAGE);
  private readonly api = inject(API_BASE_URL);

  isExpired(token: Token) {
    return token.expiresAt < this.clock.now();
  }
  refresh() {
    return this.http.post(`${this.api}/auth/refresh`, { rt: this.storage.getItem('refresh') });
  }
}
```

```ts
// тест: никакой магии с таймерами
TestBed.configureTestingModule({
  providers: [
    { provide: CLOCK, useValue: { now: () => 1_000 } },
    { provide: API_BASE_URL, useValue: '/api' },
    { provide: TOKEN_STORAGE, useValue: { getItem: () => 'rt-1', setItem: () => {} } },
    provideHttpClient(),
    provideHttpClientTesting(),
  ],
});
expect(TestBed.inject(SessionService).isExpired({ expiresAt: 999 } as Token)).toBe(true);
```

Почему лучше: `InjectionToken` с `providedIn: 'root'` и `factory` даёт дефолт без регистрации в `app.config.ts`, а тест или SSR подменяют его одной строкой. `API_BASE_URL` задаётся при сборке приложения (или из runtime-конфига, загруженного в `provideAppInitializer`), поэтому один и тот же артефакт можно деплоить на разные окружения. Абстрактный класс как токен (как вчера с `ReportExporter`) уместен, когда реализаций несколько и их выбирает место сборки; если нужен только дефолт и подмена в тестах, токен с фабрикой короче.

**Где перегибают.** Обёртки над тем, что уже является абстракцией. `IHttpService` поверх `HttpClient` «чтобы можно было заменить на fetch» — классический пример: `HttpClient` уже инвертирован (бэкенд подменяется через `withFetch()`, тесты — через `provideHttpClientTesting()`), а обёртка съедает интерцепторы, `HttpContext` и типизацию. То же с `ILogger` над `ErrorHandler` и с абстракцией над store, у которого единственная реализация и нет планов на вторую. Инвертировать стоит платформу, время, конфиг и внешние SDK, а не сам фреймворк.

## Шпаргалка для ревью

| Принцип | Вопрос на ревью | Красный флаг в Angular | Перегиб |
|---|---|---|---|
| S | Кто попросит это изменить? | Интерцептор/компонент на 4+ темы | Разрез 40-строчного компонента на 5 файлов |
| O | Как добавить N+1-й вариант? | Растущий `@switch` в общем ui-компоненте | 30 input-ов «на будущее» |
| L | Что ждёт потребитель, кроме типов? | `writeValue` вызывает `onChange` | Запрет любого `extends` |
| I | Что из этого реально используется? | `inject(BigStore)` ради одного сигнала | Reader/Writer у каждого сервиса |
| D | Откуда берутся время, окно, конфиг? | `Date.now()`, `localStorage`, `environment` в логике | Обёртка над `HttpClient` |

**Зачем это тимлиду:** «good vs bad» — это готовый материал для командного гайда и для ревью без вкусовщины. Комментарий «writeValue не должен вызывать onChange — форма станет dirty после patchValue (L)» принимается быстрее, чем «так не делают». А колонка «перегиб» защищает команду от обратной крайности: сеньор, впервые прочитавший про SOLID, способен утроить число файлов за спринт.

**Применить завтра:**

- Пройдитесь по `app.config.ts` и интерцепторам: если какой-то интерцептор делает больше одной вещи из списка «auth / retry / ошибки / метрики / кеш», разрежьте его и зафиксируйте порядок в одном месте с комментарием.
- Заведите в дизайн-системе общий тест «CVA contract» (pristine после `patchValue`, touched после blur, `disable()`, `reset()` с `null`) и прогоните через него все кастомные контролы — обычно падает минимум один.
