# 💻 День 19 · 2026-11-02 · architecture: Feature-Sliced и доменная структура фронтенда

**Коротко:** папки `components/`, `services/`, `models/` отвечают на вопрос «что это за файл», а разработчику почти всегда нужен ответ «к какой части продукта это относится и кто от кого может зависеть». Feature-Sliced Design (FSD) и доменная нарезка в духе Nx решают именно это: код группируется по бизнес-смыслу, а зависимости разрешены только в одну сторону.

**Как устроен FSD.** Три уровня. **Слои** (layers) сверху вниз: `app` (bootstrap, роутинг, провайдеры) → `pages` (экраны) → `widgets` (крупные самостоятельные блоки страницы) → `features` (пользовательские действия с ценностью: «добавить в корзину», «сменить пароль») → `entities` (бизнес-сущности: `user`, `order`, `product`) → `shared` (UI-кит, http-клиент, утилиты без бизнес-смысла). Внутри слоя — **слайсы** по домену (`features/cart-add`, `entities/order`), внутри слайса — **сегменты** по назначению: `ui`, `model`, `api`, `lib`, `config`. Главное правило одно: **модуль импортирует только из слоёв ниже**, и слайсы одного слоя не импортируют друг друга. Второе правило: у слайса есть **публичный API** (`index.ts`), снаружи импортируют только его, а не внутренние файлы.

**Нюансы, о которые спотыкаются.** Первый: граница между `features` и `entities`. Сущность — это «что» (модель заказа, карточка заказа, запрос за заказом), фича — это «действие пользователя над сущностями» (оформить заказ). Если в `entities/order` появился метод `checkout()`, который дёргает корзину и платёжку, — это фича, которая спряталась. Второй: две сущности ссылаются друг на друга (`order` показывает `user`). В FSD для этого есть явный кросс-импорт через нотацию `@x` (`entities/user/@x/order.ts`) — это не лазейка, а честная пометка связи, которую видно на ревью. Третий: `shared` превращается в свалку. Критерий простой: если в файле есть слово из предметной области (`Invoice`, `Tenant`), ему не место в `shared`. И последний: в небольшом приложении шесть слоёв — оверинжиниринг. Сами авторы методологии в версии 2.1 советуют **pages first**: держать код в странице, пока он не понадобится второй странице, и только тогда выносить вниз.

**Как это ложится на Angular и Nx.** FSD родился в React-мире, но в Angular переносится почти один в один: `pages` — это lazy-маршруты (`loadComponent` / `loadChildren`), `app` — `app.config.ts` и `app.routes.ts`, а сегмент `model` — это сервис со стейтом на сигналах или SignalStore. В Nx-монорепо тот же принцип уже знаком из урока про монорепо: теги `scope:<домен>` (вертикаль, аналог слайса) и `type:feature|ui|data-access|util` (горизонталь, аналог слоя), а `enforce-module-boundaries` запрещает импорт против течения. По сути Nx-таксономия — это FSD с четырьмя слоями вместо шести. Без Nx правило можно проверять линтером Steiger (официальный для FSD) или `eslint-plugin-boundaries`.

```ts
// pages/order-details/ui/order-details.page.ts
import { OrderCard } from '@/entities/order';          // ✅ вниз, через публичный API
import { RepeatOrderButton } from '@/features/order-repeat'; // ✅ вниз
// import { CartStore } from '@/features/cart-add/model/cart.store'; // ❌ в обход index.ts
// import { HeaderWidget } from '@/widgets/header';     // ✅ формально можно, но страница не должна знать про layout

@Component({
  selector: 'app-order-details-page',
  imports: [OrderCard, RepeatOrderButton],
  template: `
    <app-order-card [order]="order()" />
    <app-repeat-order-button [orderId]="order().id" />
  `,
})
export class OrderDetailsPage {
  readonly order = input.required<Order>(); // из резолвера через withComponentInputBinding
}
```

**Зачем это тимлиду:** структура — это способ масштабировать команду, а не код. Когда у каждого домена есть понятная папка и публичный API, по ней можно раздать владение (CODEOWNERS по `entities/billing`), новичок находит нужное без экскурсии, а ревью «можно ли тут импортировать» превращается из спора о вкусе в проверку линтера. Обратная сторона: миграцию большого проекта нельзя сделать одним PR — это месяцы постепенного переноса, и это решение надо продать команде, а не спустить сверху.

**Применить завтра:**

- Возьми один «горячий» раздел приложения и нарисуй на доске его граф импортов. Если стрелки идут во все стороны — это и есть аргумент для команды, а не «так модно».
- Договоритесь о правиле публичного API (`index.ts` на каждую доменную папку, импорт только через него) и включите его в линтер. Это даёт 70% пользы FSD без переезда всех файлов.
