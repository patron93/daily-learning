### 📖 Грамматика: как читать sz/cz/rz/ż, ś/ć/ń/ź, ą/ę, ó

Хорошая новость: польская орфография почти полностью фонетическая. Если знаешь 15 правил, прочтёшь любое слово. Русскоязычным проще всего опираться на русские звуки.

**1. «Твёрдые» шипящие (как в русском, даже твёрже):**
- **sz** = ш: *szef* [шеф], *szybko* [шыпко] — быстро
- **cz** = ч, но твёрдое, ближе к «чш»: *czas* [час] — время
- **ż** и **rz** = ж (звучат одинаково, пишутся по-разному по историческим причинам): *żona* [жона], *rzeka* [жэка] — река
- После глухих согласных **rz** оглушается в ш: *przerwa* [пшэрва], *trzy* [тшы] — три. Здесь сильно помогает белорусский: *тры*, *рака*: там тоже на месте старого мягкого «р».
- **dż** = дж, **dz** = дз (как белорусское «дз»: *dzwon* [дзвон])

**2. «Мягкие» шипящие — отдельная серия звуков:**
- **ś / si** = мягкое щ-подобное «сь»: *śniadanie* [сьнядане] — завтрак, *siedem* — семь
- **ć / ci** = «ць» (почти ч мягкое): *cześć* [чэщьць], *ciocia* — тётя
- **ź / zi** = мягкое «жь»: *źle* — плохо, *zima* — зима
- **ń / ni** = нь: *koń* — конь, *nie* [не]
- Правило: перед гласной пишут **si/ci/zi/ni**, в конце слова или перед согласной — **ś/ć/ź/ń**. *Ciocia* и *cześć* — один и тот же звук «ць».
- Самое трудное для нас: различать **cz** (твёрдое) и **ć** (мягкое). *Czy* [чы] vs *ci* [ци с мягкостью].

**3. Носовые ą / ę:**
- **ą** = «он/ом», **ę** = «эн/эм» перед согласными: *ręka* [рэнка], *ząb* [зомп], *dziękuję* [дзенькуе].
- В конце слова **ę** почти не слышно: *proszę* [прошэ], а **ą** звучит как носовое «о(у)»: *są* [со(н)].

**4. Ó = u.** *Ó* и *u* звучат одинаково (у): *góra* [гура] — гора, *kłótnia* — ссора. Подсказка из русского: там, где в польском *ó*, в русском часто стоит «о»: *mój* — мой, *wóz* — воз, *ból* — боль.

**Бонус:** **ł** = английское w (почти «у»): *łyżka* [уышка], *mały* [мауы]. А **w** = в: *woda* [вода].

## 💻 Профразвитие · Angular: Signals глубже — computed, effect и когда effect становится антипаттерном

**Коротко:** `computed` — это чистое производное значение с ленивым мемоизированным пересчётом; `effect` — побочный эффект «наружу». Большинство `effect`, которые синхронизируют один сигнал с другим, должны быть `computed` или `linkedSignal`.

**Как устроен граф.** Сигналы образуют граф зависимостей «push-pull». При `set()` Angular не пересчитывает всё сразу: он только помечает зависимые узлы как «грязные» (push). Значение `computed` пересчитывается лениво, при следующем чтении (pull), и только если изменилась хотя бы одна зависимость (по сравнению через `equal`, по умолчанию `Object.is`). Отсюда два следствия: `computed`, который никто не читает, ничего не стоит, а зависимости динамические: в `computed(() => flag() ? a() : b())` в каждый момент отслеживается только одна из веток.

**Effect и его тайминг.** С v19 эффекты поделены на два вида: эффекты компонентов выполняются в процессе change detection (до проверки шаблона этого компонента), а «root»-эффекты (созданные в сервисах) — как микротаск перед CD. С тех пор запись в сигналы внутри `effect` разрешена по умолчанию (флаг `allowSignalWrites` удалили). Это удобно, но открыло дорогу главному антипаттерну: каскадам `effect → set → effect`, которые сложно отлаживать, вызывают лишние проходы CD и легко приводят к промежуточным «несогласованным» состояниям. Для работы с DOM после рендера есть отдельный `afterRenderEffect`.

**Правило большого пальца:** `effect` нужен, когда результат уходит **за пределы** графа сигналов: localStorage, аналитика, логирование, ручной вызов стороннего API (canvas, карты, графики). Если результат — другое состояние в приложении, это `computed` (только чтение) или `linkedSignal` (производное, но с возможностью локально переопределить). Для асинхронных данных — `resource`/`httpResource`, а не `effect` с `subscribe` внутри.

```ts
// ❌ Антипаттерн: синхронизация сигналов через effect
export class UserListComponent {
  users = input.required<User[]>();
  filter = signal('');
  filtered = signal<User[]>([]);
  selected = signal<User | null>(null);

  constructor() {
    effect(() => {
      this.filtered.set(this.users().filter(u => u.name.includes(this.filter())));
    });
    effect(() => this.selected.set(this.users()[0] ?? null)); // сброс выбора
  }
}

// ✅ То же самое без effect
export class UserListComponent {
  users = input.required<User[]>();
  filter = signal('');

  filtered = computed(() =>
    this.users().filter(u => u.name.includes(this.filter()))
  );

  // производное, но пользователь может выбрать другое значение
  selected = linkedSignal(() => this.users()[0] ?? null);

  constructor() {
    // ✅ Законный effect: побочный эффект наружу
    effect(() => localStorage.setItem('userFilter', this.filter()));
  }
}
```

Пара нюансов: внутри `effect` используй `untracked()` для чтений, которые не должны становиться зависимостями (например, логгер, читающий текущего пользователя), и `onCleanup` для отмены таймеров и подписок. Для `computed` от объектов передавай свой `equal`, если важно не будить потребителей при структурно одинаковом результате.

**Зачем это тимлиду:** в командах, которые только переходят на сигналы, `effect` быстро становится новым «`subscribe` в `ngOnInit`»: императивная синхронизация, которая выглядит как реактивность. Если зафиксировать правило в гайдлайнах сейчас, кодовая база не наполнится цепочками эффектов, которые потом придётся распутывать.

**Применить завтра:**
- Сделай в репозитории поиск `effect(` и пройдись по результатам с вопросом «это уходит наружу или это производное состояние?». Каждый `this.x.set(...)` внутри `effect` — кандидат на `computed`/`linkedSignal`.
- Добавь в чек-лист code review пункт: «`effect` записывает в сигнал → нужна причина в комментарии».

**Почитать:** [angular.dev — Effects: когда использовать и когда нет](https://angular.dev/guide/signals/effect), плюс [Angular Architects — When (Not) to use Effects](https://www.angulararchitects.io/?p=26617)
