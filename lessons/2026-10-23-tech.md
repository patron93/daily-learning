# 💻 День 9 · 2026-10-23 · Angular: linkedSignal и resource / httpResource

**Коротко:** `linkedSignal` — это writable-состояние, которое само сбрасывается, когда меняется источник. `resource` / `httpResource` — асинхронные данные в виде сигналов со статусом, ошибкой и отменой запроса. С Angular 22 resource-семейство стабильно, так что этим уже можно закрывать ручные `loading`/`error`-флаги и половину `switchMap` в компонентах.

### linkedSignal: «состояние по умолчанию из источника, но пользователь может поменять»

Классическая задача: есть список вариантов доставки (пришёл сверху через `input()`), и есть выбранный вариант. Пользователь выбирает что-то своё, но когда список меняется, выбор надо сбросить или сохранить, если он ещё валиден. `computed` не подходит: он read-only. `signal` + `effect` работает, но это ровно тот антипаттерн «effect синхронизирует состояние» из урока про сигналы (день 1): лишний проход change detection и гонки.

`linkedSignal` закрывает это одним примитивом. Короткая форма `linkedSignal(() => source()[0])` пересчитывается при изменении источника, но между пересчётами в неё можно делать `set()`/`update()`. Длинная форма `{ source, computation }` даёт в `computation` второй аргумент `previous` — прошлые значение источника и самого сигнала. Это и есть главный нюанс: можно **сохранить выбор пользователя, если он всё ещё есть в новом списке**.

```ts
readonly options = input.required<ShippingOption[]>();

readonly selected = linkedSignal<ShippingOption[], ShippingOption | undefined>({
  source: this.options,
  computation: (opts, previous) =>
    opts.find(o => o.id === previous?.value?.id) ?? opts[0],
  equal: (a, b) => a?.id === b?.id,
});

choose(option: ShippingOption) {
  this.selected.set(option); // локальная правка, до следующей смены options
}
```

### resource: асинхронность как состояние

`resource({ params, loader })` превращает промис в набор сигналов: `value`, `status` (`'idle' | 'loading' | 'reloading' | 'resolved' | 'error' | 'local'`), `error`, `isLoading`, `hasValue()`, плюс `reload()`, `set()`/`update()`. Нюансы, которые стоит знать до код-ревью:

- **`params` — реактивная часть, `loader` — нет.** Сигналы, прочитанные внутри `loader`, не отслеживаются. Всё, от чего зависит запрос, должно быть в `params`.
- **`params` вернул `undefined` — статус `'idle'`, loader не вызывается.** Это штатный способ сказать «пока не грузи» (например, id ещё не выбран), без `filter` и `if` в loader.
- **Отмена встроена.** Если `params` изменились во время загрузки, предыдущая операция отменяется через `abortSignal`. Его надо передать в `fetch`, иначе запрос всё равно уйдёт до конца (`httpResource` делает это сам).
- **`value()` в статусе `'error'` бросает исключение.** В шаблоне и `computed` сначала проверяйте `hasValue()`.
- **`set()` переводит ресурс в `'local'`** — удобно для оптимистичных апдейтов: показали новое значение сразу, а после ответа сервера сделали `reload()`.

`rxResource` — то же самое, но с `stream`, который возвращает Observable (если источник уже на RxJS). `httpResource` — обёртка над `HttpClient`: идёт через интерцепторы, сам отменяет запросы, поддерживает `defaultValue` и `parse` (например, Zod-схему для валидации ответа), а также варианты `httpResource.text()`, `.blob()`, `.arrayBuffer()`.

```ts
@Component({
  template: `
    @if (user.hasValue()) {
      <app-user-card [user]="user.value()" />
    } @else if (user.error()) {
      <app-error (retry)="user.reload()" />
    } @else if (user.isLoading()) {
      <app-skeleton />
    }
  `,
})
export class UserPage {
  readonly userId = input<string>();

  // undefined → idle, смена id → отмена старого запроса и новый GET
  readonly user = httpResource<User>(() => {
    const id = this.userId();
    return id ? `/api/users/${id}` : undefined;
  });

  // Зависимый ресурс: пока нет пользователя — idle, без лишнего запроса
  readonly orders = httpResource<Order[]>(
    () => this.user.hasValue()
      ? { url: '/api/orders', params: { userId: this.user.value().id } }
      : undefined,
    { defaultValue: [] },
  );
}
```

Для цепочек на `resource()` в v22 появился `chain()`: он доступен в контексте `params` (`params: ({ chain }) => chain(userResource)?.companyId`) и прокидывает статус родителя вниз — если родитель упал, дочерний ресурс получит `ResourceDependencyError`, а не зависнет в `idle`. Для синхронных производных значений по-прежнему берите `computed`.

**Где граница с RxJS.** `resource` хорош для «загрузить по параметрам и показать». Он не заменяет RxJS для сложной оркестрации: дебаунс с `distinctUntilChanged`, ретраи с backoff, объединение нескольких потоков, WebSocket-логика. Это остаётся в сервисах на RxJS, а наружу отдаётся через `rxResource` или `toSignal`. И `resource` — про **чтение**: мутации (POST/PUT/DELETE) по-прежнему делайте явным вызовом `HttpClient` в обработчике, а не через `params`.

**Зачем это тимлиду:** это меняет «канонический» способ загрузки данных в компоненте. Если не договориться, в кодовой базе одновременно будут жить `subscribe` + флаги, `async`-пайп, `toSignal(switchMap)` и `httpResource`, и каждый новый человек будет выбирать наугад. Плюс у ресурсов есть свои грабли (реактивность только в `params`, `value()` бросает при ошибке, мутации не через ресурс), и их проще зафиксировать в гайде один раз, чем ловить на ревью.

**Применить завтра:**

- Найдите в проекте 2–3 компонента с ручными `loading`/`error`-флагами и `takeUntilDestroyed` вокруг GET-запроса и перепишите один на `httpResource` как эталон. Сравните объём кода и поведение при быстрой смене параметра.
- Добавьте в гайд команды короткое правило: чтение — `httpResource`/`resource`, мутации — `HttpClient` в обработчике, сложная оркестрация — RxJS в сервисе; состояние «по умолчанию из входа, но редактируемое» — `linkedSignal`, а не `effect`.
