# 💻 День 14 · 2026-10-28 · backend: NestJS для Angular-разработчика: те же идеи DI и декораторов

**Коротко:** NestJS выглядит как Angular на сервере: декораторы, модули, `@Injectable`, интерцепторы на RxJS. Это сильно ускоряет вход для фронтенд-команды, но три вещи работают иначе, и именно на них Angular-разработчики ловят продовые баги: синглтон живёт на весь процесс, модули жёстко инкапсулируют провайдеры, а запрос проходит через конвейер из пяти разных механизмов.

**Что знакомо.** Контроллер — это «компонент» для HTTP: класс с декораторами `@Controller('orders')`, `@Get(':id')`, `@Body()`. Сервисы — `@Injectable()`, инжектятся по типу через конструктор, токены для интерфейсов и конфигов — через `@Inject(TOKEN)`, как `InjectionToken`. Есть `useClass`, `useValue`, `useFactory`, `useExisting` с тем же смыслом. Интерцепторы возвращают `Observable`, и в них работают привычные `map`, `tap`, `catchError`, `timeout`. На этом сходство заканчивается.

**Что иначе.** (1) **Синглтон на процесс, а не на пользователя.** В Angular `providedIn: 'root'` — это один экземпляр на вкладку браузера, то есть фактически на одного пользователя. В Nest провайдер по умолчанию один на всё приложение, и его делят все параллельные запросы. Поле `currentUser` в сервисе, привычное на фронте, на бэкенде — утечка данных между пользователями. Есть `Scope.REQUEST`, но он «всплывает»: все, кто зависит от request-scoped провайдера, тоже становятся request-scoped и создаются на каждый запрос, что бьёт по производительности. Обычно лучше передавать контекст аргументом или хранить его в `AsyncLocalStorage` (готовая обёртка — `nestjs-cls`). (2) **Модули обязательны и инкапсулируют.** Standalone здесь нет; провайдер виден только внутри своего модуля, пока его не добавили в `exports`, а потребитель не сделал `imports`. Знаменитая ошибка `Nest can't resolve dependencies of OrdersService (?)` почти всегда значит «забыли export/import». `@Global()` существует, но это аналог «всё в root»: удобно, пока не понадобятся границы. (3) **Только конструктор.** Функции `inject()` в Nest нет, инъекция по типу опирается на метаданные `emitDecoratorMetadata`, поэтому `import type` для инжектируемого класса ломает DI.

**Конвейер запроса.** Порядок: middleware → guards → interceptors (до) → pipes → обработчик → interceptors (после) → exception filters. Guard решает «пускать ли» (как `CanActivate` у роутера), pipe валидирует и преобразует аргументы, interceptor оборачивает выполнение (логи, кеш, таймауты, маппинг ответа), filter превращает исключение в HTTP-ответ (как `ErrorHandler`, но с выбором статуса). Классическая ошибка — проверять права в interceptor или валидировать в guard: работает, но ломает ожидания команды и порядок. В NestJS 12 (релиз 27 августа 2026) ядро перешло на ESM, а валидация открылась для Standard Schema: Zod-схему можно передать прямо в `@Body({ schema })`, если глобально зарегистрирован `StandardSchemaValidationPipe`. Классический `ValidationPipe` с `class-validator` продолжает работать.

```ts
// orders.module.ts — границы как у feature-библиотеки
@Module({
  imports: [PaymentsModule],          // PaymentsModule должен экспортировать PaymentsService
  controllers: [OrdersController],
  providers: [OrdersService, { provide: CLOCK, useValue: () => new Date() }],
  exports: [OrdersService],           // без этого соседние модули его не увидят
})
export class OrdersModule {}

// ❌ Привычка с фронта: состояние пользователя в синглтоне
@Injectable()
export class OrdersService {
  private currentUserId?: string;     // общий для ВСЕХ параллельных запросов
}

// ✅ Контекст приходит из запроса и передаётся явно
@Controller('orders')
@UseGuards(AuthGuard)
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @Post()
  create(@Req() req: AuthedRequest, @Body({ schema: createOrderSchema }) dto: CreateOrder) {
    return this.orders.create(req.user.id, dto);
  }
}
```

**Зачем это тимлиду:** Nest — самый короткий путь для Angular-команды к своему BFF или небольшому сервису: общий TypeScript, общие DTO и схемы в монорепо, знакомая ментальная модель. Но именно знакомость опасна: код «как на фронте» проходит ревью, потому что выглядит правильно. Ваша задача — заранее назвать различия (время жизни провайдеров, границы модулей, что куда в конвейере) и закрепить их в правилах ревью и `AGENTS.md`, тем более что агенты охотно переносят фронтовые привычки на сервер.

**Применить завтра:**

- Если у вас уже есть Nest-сервис, сделайте grep по `private .*: ` в `@Injectable`-классах и проверьте каждое изменяемое поле: не хранит ли оно данные запроса или пользователя. Это 20 минут, которые иногда находят реальную утечку.
- Добавьте в гайд команды табличку «где что живёт»: аутентификация и роли — guard, валидация — pipe, логи/таймауты/маппинг ответа — interceptor, ошибки в HTTP — filter. На ревью ссылайтесь на неё, а не спорьте каждый раз.
