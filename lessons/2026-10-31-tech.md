# 💻 День 17 · 2026-10-31 · leadership: Code review как инструмент роста, а не бутылочное горлышко

**Коротко:** ревью в команде делает две работы — защищает здоровье кодовой базы и распространяет знания. Если тимлид обязательный апрувер каждого PR, обе работы проваливаются: очередь растёт, а команда учится не думать, а «проходить тимлида».

**Как ревью превращается в горлышко.** Симптомы узнаются сразу: PR висит два дня в ожидании «того самого человека»; авторы копят изменения в один PR на 1500 строк, «чтобы не ждать дважды»; в комментариях смешаны блокирующие баги и вкусовщина про имена переменных, и автор не понимает, что из этого обязательно. Хуже всего вторичный эффект: если всё проверяет сеньор, остальные перестают ревьюить всерьёз («он всё равно посмотрит») — и bus factor по знанию кода падает до единицы. Исследования Microsoft (Bacchelli & Bird, «Expectations, Outcomes, and Challenges of Modern Code Review») показали неожиданное: разработчики ждут от ревью поиска багов, а главная фактическая польза — **передача знаний и общее понимание кода**. Значит, ревью, которое делает один человек, теряет основную ценность.

**Планка «лучше, а не идеально».** В открытом гайде Google по ревью главный принцип звучит так: ревьюер одобряет изменение, если оно **улучшает общее здоровье кода**, даже если оно не идеально; совершенства не бывает, бывает постоянное улучшение. Второе правило — скорость: отвечать на ревью нужно быстро, максимум в течение одного рабочего дня, потому что медленное ревью тормозит всю команду и толкает людей к огромным PR. Третье — помечать необязательное: Google советует префикс «Nit:», чтобы автор видел, что это шлифовка, а не блокер. Отсюда простое правило для тимлида: **ревью оценивает направление и риски, а не «написал бы я так же»**.

**Ревью как обучение.** Комментарий растит человека, когда объясняет «почему» и оставляет ему решение. Сравни «перепиши на `computed`» и «здесь `effect` пишет в другой сигнал — это даст лишний цикл CD и сложнее тестировать; `computed` выразит то же декларативно, как думаешь?». Для этого удобна договорённость **Conventional Comments**: метка в начале комментария (`praise`, `nitpick`, `suggestion`, `issue`, `question`, `thought`) плюс пометка `(blocking)` / `(non-blocking)`. Автор сразу видит вес замечания, а спор о вкусе перестаёт выглядеть как запрет мержа. И не забывай `praise:` — хорошее решение, отмеченное в ревью, закрепляется лучше, чем исправленная ошибка.

```ts
// PR: фича «фильтры в списке заказов» (Angular)

// issue (blocking): подписка без отписки — при уходе со страницы
// поток живёт дальше. takeUntilDestroyed(this.destroyRef) или toSignal().
this.filters$.subscribe(f => this.load(f));

// suggestion (non-blocking): фильтры — это состояние URL,
// а не только компонента. queryParams дадут шаринг ссылки и «назад».
filters = signal<OrderFilters>(DEFAULT_FILTERS);

// question: зачем тут ChangeDetectorRef.detectChanges()?
// Если без него не обновляется — давай найдём, кто мутирует объект.

// nitpick (non-blocking): isLoad → isLoading, но не блокирует.

// praise: вынос маппинга DTO → модель в отдельную функцию 👍,
// её легко покрыть юнит-тестом.
```

**Как разгрузить тимлида, не теряя качества:**

- **Автоматизируй всё механическое.** Prettier, ESLint с `angular-eslint`, `strict` в tsconfig, проверка размера бандла и тесты в CI. Всё, что поймала машина, не должно стать комментарием человека.
- **Маленькие PR.** Внимание ревьюера быстро падает на больших диффах; ориентир — до ~400 строк, лучше меньше. Помогают feature flags и stacked PR: фича мержится по частям за флагом.
- **Ротация ревьюеров.** `CODEOWNERS` на команду, а не на конкретного человека, и автоназначение ревьюеров в GitHub/GitLab по кругу. Пара «джун + сеньор» на один PR: джун учится читать чужой код, сеньор страхует.
- **SLA на ревью.** Первый ответ — в течение рабочего дня (или «до конца дня, если PR пришёл до обеда»). Меряй время до первого ревью и время жизни PR, а не число комментариев.
- **Тимлид — не обязательный апрувер.** Тимлид ревьюит выборочно: архитектурно рискованное (публичные API, shared-библиотеки, безопасность) и PR людей, которых сейчас учит. Остальное — уровень делегирования 6–7 из урока про делегирование.

**Зачем это тимлиду:** ревью — самый частый и дешёвый канал обучения в команде: десятки маленьких разговоров о коде каждую неделю. Если он работает через одного человека, ты получаешь очередь, выгорание и команду, которая без тебя не может смержить. Если через всех — растут и люди, и общее знание кода.

**Применить завтра:**

- Предложи команде Conventional Comments на две недели как эксперимент и попроси в каждом PR оставлять хотя бы один `praise:`.
- Посмотри, сколько открытых PR сейчас ждут именно тебя. Для половины из них назначь другого ревьюера и поставь себе задачу ревьюить только рискованные изменения.
