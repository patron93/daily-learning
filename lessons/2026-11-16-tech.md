# 💻 День 33 · 2026-11-16 · architecture: State management — пять видов состояния и у каждого свой хозяин

**Коротко:** спор «NgRx или сервисы с сигналами?» обычно идёт не о том. Сначала нужно разложить состояние по видам: **серверное**, **URL**, **форма**, **локальное UI** и **глобальное клиентское**. У каждого вида свой источник правды и свой инструмент, и когда это сделано, «глобального стора» остаётся удивительно мало. В Angular 22 под каждый вид наконец есть стабильный примитив: `httpResource`, router input binding, Signal Forms, `signal`/`computed`.

**Почему классификация важнее библиотеки.** Типичный стор в зрелом Angular-приложении — это свалка: список заказов с бэкенда, флаг `isSidebarOpen`, текущая страница пагинации, черновик формы и `currentUser`. Каждая из этих вещей живёт по своим законам, и стор заставляет их жить по одному. Серверные данные **не ваши**: вы держите копию, которая устаревает, поэтому нужны загрузка, ошибка, инвалидация и повторный запрос — это кеш, а не состояние. URL-состояние должно переживать перезагрузку, «назад» и ссылку, кинутую коллеге в Slack; если фильтр живёт в сторе, а не в query params, ссылка «посмотри вот эти заказы» не работает. Состояние формы — это черновик с собственной валидацией, `dirty`/`touched` и своим жизненным циклом; оно не должно попадать в общий стор до сабмита. Локальное UI-состояние (раскрыт ли аккордеон, какой таб выбран) умирает вместе с компонентом и никому больше не нужно. И только остаток — сессия пользователя, feature flags, корзина, которая собирается на нескольких экранах, — это настоящее глобальное клиентское состояние.

**Шестой вид, которого не должно быть в сторе: производное.** «Итоговая сумма корзины», «есть ли непрочитанные», «отфильтрованный список» — это не состояние, а функция от состояния. Его нельзя хранить: как только вы его храните, появляется второй источник правды и баги рассинхронизации. В Angular это `computed()`. Правило ревью простое: если значение можно вычислить из другого — это `computed`, а не `signal` с `effect`, который его «синхронизирует» (тот самый антипаттерн из урока про `effect` от 15 октября).

**Что изменилось в Angular 22.** В v22 (июнь 2026) стабильны `resource()`, `rxResource()` и `httpResource()` — с хелпером `chain()` для зависимых запросов, а **Signal Forms** вышли из экспериментального статуса. `withComponentInputBinding()` получил опции: можно отключить привязку query params к инпутам (`queryParams: false`) и выбрать поведение для «чужих» инпутов (`unmatchedInputBehavior`). И ещё один сдвиг: **OnPush теперь по умолчанию**, а старый `Default` переименован в `Eager`. Это значит, что «мутирую объект в сервисе и надеюсь, что экран обновится» окончательно перестало работать: состояние должно быть реактивным, а значит, у него должен быть понятный хозяин.

![Пять видов состояния: источник правды и инструмент в Angular 22](/img/tech/2026-11-16-state-kinds.svg)

| Вид | Источник правды | Живёт | Инструмент в Angular 22 |
|---|---|---|---|
| Серверное | бэкенд | пока данные свежие | `httpResource` / `resource`, TanStack Query |
| URL | адресная строка | перезагрузка, ссылка, «назад» | router + `input()` через `withComponentInputBinding` |
| Форма | черновик пользователя | до сабмита или ухода | Signal Forms (`form()`), reactive forms |
| Локальное UI | компонент | пока жив компонент | `signal()` в компоненте |
| Глобальное клиентское | приложение | сессия | сервис с сигналами или SignalStore |
| Производное | — (не хранится) | — | `computed()` |

```ts
// Экран «Заказы»: каждый вид состояния — у своего хозяина
@Component({ /* ... OnPush уже по умолчанию в v22 */ })
export class OrdersPage {
  private router = inject(Router);

  // URL-состояние: фильтр и страница приходят из ?status=...&page=...
  status = input<'open' | 'closed'>('open');
  page = input(1, { transform: numberAttribute });

  // Серверное состояние: кеш ответа, с loading/error из коробки
  orders = httpResource<OrderPage>(() => ({
    url: '/api/orders',
    params: { status: this.status(), page: this.page() },
  }));

  // Локальное UI: никому, кроме этого компонента, не нужно
  expandedId = signal<string | null>(null);

  // Производное: не храним, вычисляем
  overdueCount = computed(
    () => this.orders.value()?.items.filter(o => o.overdue).length ?? 0,
  );

  // Глобальное клиентское: только то, что правда общее
  private session = inject(SessionStore);
  canEdit = computed(() => this.session.role() === 'manager');

  // Меняем фильтр через URL, а не через стор: ссылка остаётся рабочей
  setStatus(status: 'open' | 'closed') {
    this.router.navigate([], {
      queryParams: { status, page: 1 },
      queryParamsHandling: 'merge',
    });
  }
}
```

Обрати внимание, чего здесь нет: нет `ngOnInit` с подпиской на `queryParamMap`, нет `effect`, который перезапрашивает данные при смене фильтра, нет экшенов `loadOrders`/`loadOrdersSuccess`/`loadOrdersFailure`. Реактивная цепочка «URL → инпут → `httpResource` → `computed` → шаблон» строится декларативно, а состояние формы (например, диалог редактирования заказа) живёт в своём `form()` и уходит на сервер только при сабмите, после чего достаточно `orders.reload()`.

**Где классический стор всё ещё нужен.** NgRx Store (или SignalStore с событиями) оправдан, когда много экранов **пишут** в одно и то же клиентское состояние, нужна история действий (undo, аудит, отладка в DevTools), есть оптимистичные обновления с откатом или офлайн-режим. Это реальные случаи — редактор документов, конструктор, сложная корзина. Но если 80% вашего стора — это ответы бэкенда с флагами `loading`, вы держите в нём кеш, который `httpResource` или TanStack Query сделают лучше и с меньшим кодом.

**Зачем это тимлиду:** большинство споров «какой стейт-менеджер взять» на самом деле спор о вещах, которые в стор класть не надо. Таблица видов состояния даёт команде общий язык для ревью: «это серверное — почему оно в сторе?», «это URL — почему ссылка не воспроизводит экран?», «это производное — почему оно хранится?». Это снижает количество кода и, главное, багов рассинхронизации, которые тяжелее всего ловить. А переход на OnPush по умолчанию в v22 — удобный повод провести такую ревизию сейчас, а не во время пожара.

**Применить завтра:**

- Возьми самый большой feature-стор и разметь каждое поле одной буквой: S (server), U (URL), F (form), L (local), G (global), D (derived). Всё, что не G, — кандидаты на вынос. Обычно G оказывается 10–20%.
- Добавь в чек-лист ревью вопрос: «Если я скопирую URL этого экрана и открою в новой вкладке, увижу ли я то же самое?» Если нет, фильтры и пагинация живут не там.
