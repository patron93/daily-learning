# 💻 День 22 · 2026-11-05 · classic: «Clean Code» с критикой — что устарело, а что нет

**Коротко:** «Clean Code» Роберта Мартина (2008) — книга, по которой учились почти все сеньоры, и в ней по-прежнему много верного: имена, отсутствие дублирования, тесты, маленькие осмысленные модули. Но несколько её правил, применённых буквально, делают код **хуже**: функции на 3–4 строки, «комментарий — это провал», борьба с аргументами любой ценой. Тимлиду важно не «за» или «против», а уметь объяснить команде, **где правило работает, а где превращается в карго-культ**.

**Что устарело или спорно.** Главный спор лучше всего задокументирован в публичной дискуссии Джона Остераута (автор «A Philosophy of Software Design») и самого Мартина, которая шла с сентября 2024 по февраль 2025 и выложена на GitHub. **Длина функций.** Мартин советует очень короткие методы, которые делают «одну вещь». Остераут показывает, что при пересплите методы становятся **мелкими (shallow)** и **сцепленными (entangled)**: чтобы понять одну, надо держать в голове пять соседних, а их общие данные утекают в поля класса. Его критерий другой — **глубокий модуль**: простой интерфейс, за которым спрятано много логики. В той же дискуссии нашлось и забавное: в учебном примере Мартина разбиение цикла на «чистые» кусочки замедлило код в 3–4 раза, и автор это признал. **Комментарии.** У Мартина комментарий — «необходимое зло» и «потенциальная дезинформация». На практике отсутствие комментария «почему» стоит команде намного дороже, чем устаревший комментарий: имя функции объясняет *что*, но никогда не объяснит, *почему нельзя иначе* (баг в Safari, требование юристов, гонка с бэкендом). **Примеры кода** в книге — Java середины 2000-х: наследование, мутабельные поля, сеттеры. В TypeScript и Angular многие «запахи» решаются типами (discriminated unions вместо флагов), иммутабельностью и функциями, а не новыми классами.

**Что по-прежнему золото.** Говорящие имена и единый язык домена. Ранний выход вместо пирамиды `if`. Функции без скрытых побочных эффектов. «Правило бойскаута» — оставь код чуть чище, чем нашёл. Тесты как часть кода, а не довесок. Сам Мартин выпустил второе издание книги (Pearson): примеры обновлены, но философия коротких функций осталась. Спорить стоит с буквальным применением правил, а не с целью — код, который легко читать и менять.

**Пример: «по книге» против «глубокой» функции.** Расчёт итоговой цены корзины в Angular-сервисе:

```ts
// ❌ «Чисто» по букве: 6 крошечных методов, общие данные — в полях класса
export class CartTotal {
  private items: CartItem[] = [];
  private subtotal = 0;
  private discount = 0;

  calculate(items: CartItem[]): number {
    this.items = items;
    this.computeSubtotal();
    this.applyPromo();
    this.applyLoyalty();
    return this.roundTotal();
  }
  private computeSubtotal() { this.subtotal = this.items.reduce((s, i) => s + i.price * i.qty, 0); }
  private applyPromo() { if (this.subtotal > 200) this.discount = 0.1; }
  private applyLoyalty() { this.discount += 0.05; } // порядок вызовов критичен, но это нигде не видно
  private roundTotal() { return Math.round(this.subtotal * (1 - this.discount) * 100) / 100; }
}

// ✅ Одна чистая функция: вход → выход, порядок шагов виден, состояние не утекает
export function cartTotal(items: readonly CartItem[], isLoyal: boolean): number {
  const subtotal = items.reduce((sum, i) => sum + i.price * i.qty, 0);

  // Скидки суммируются, а не перемножаются: так прописано в условиях акции (JIRA-1423).
  const discount = (subtotal > 200 ? 0.1 : 0) + (isLoyal ? 0.05 : 0);

  return Math.round(subtotal * (1 - discount) * 100) / 100; // округляем до грошей один раз, в конце
}
```

Первый вариант формально соблюдает «маленькие функции», но держит скрытое состояние: вызови `applyLoyalty()` дважды — получишь лишние 5 %. Второй длиннее одного метода, зато его можно прочитать сверху вниз, протестировать без моков, а комментарий объясняет то, чего не скажет ни одно имя.

**Зачем это тимлиду:** правила из «Clean Code» часто живут в команде как аргумент на ревью: «функция больше 20 строк», «убери комментарий». Если тимлид не объяснит границы, правила превращаются в бюрократию: дробление ради метрики, бесполезный рефакторинг, споры о вкусе. Хороший стандарт команды — это не цитаты из книги, а **короткий список принципов с объяснением «зачем»** и примерами из вашего же кода.

**Применить завтра:**

- Пересмотри гайд по код-ревью: замени механические правила («не больше N строк», «без комментариев») на вопросы — «понятно ли, что делает функция, без чтения соседних?», «объяснено ли неочевидное *почему*?».
- На следующем техническом митинге разберите вместе 1–2 раунда из дискуссии Остераута и Мартина (длина методов и комментарии) и договоритесь, какой позиции придерживается команда. Зафиксируйте это в одном абзаце в CONTRIBUTING.md.
