# 💻 День 31 · 2026-11-14 · leadership: Tech debt — как продавать его бизнесу и планировать

**Коротко:** бизнес не покупает «рефакторинг» — он покупает скорость, предсказуемость и снижение риска. Работа тимлида — перевести долг с языка кода на язык процентов: сколько он стоит каждый спринт, что будет, если не платить, и какой план погашения у нас есть.

**Метафора, которую часто используют неправильно.** Уорд Каннингем придумал «технический долг» как *финансовую* метафору: взять кредит, чтобы быстрее выйти на рынок, — нормально, если понимаешь, что платишь проценты, пока не вернёшь основную сумму. Проценты — это не «код некрасивый», а **лишнее время и риск при каждом следующем изменении** этого места. Отсюда важное следствие: долг в модуле, который никто не трогает годами, почти бесплатный. Дорогой долг — тот, что лежит на «горячем пути»: там, куда команда заходит каждый спринт. Поэтому список «всё плохое в репозитории» — это не план, а свалка; план начинается с пересечения «плохо» × «часто меняется».

**Не весь долг одинаков.** Мартин Фаулер делит его на квадрант по двум осям: *осознанный / неосознанный* и *разумный / безрассудный*. «Выпустим сейчас, а через спринт вынесем в сервис» — осознанный и разумный: это кредит с графиком платежей. «Нет времени на дизайн» — осознанный, но безрассудный. «Что такое слои?» — безрассудный и неосознанный: это уже не долг, а пробел в навыках, и лечится он ревью и обучением, а не «спринтом рефакторинга». Отдельный и самый честный вид — разумный неосознанный: «теперь мы понимаем, как надо было сделать» — так выглядит любой живой продукт через год. Для тимлида квадрант полезен, чтобы не смешивать в одном бэклоге кредит, халтуру и устаревание: у них разные лечения.

**Как продавать: от симптома к деньгам.** Плохой питч: «Нам нужно две недели на рефакторинг стора». Хороший питч строится как продуктовое предложение:

1. **Симптом, который бизнес уже чувствует:** «фичи в checkout стабильно оцениваем в 2× дольше, чем аналогичные в каталоге; за квартал там 4 инцидента на проде».
2. **Причина в одной фразе без жаргона:** «логика оплаты размазана по 6 компонентам и общему сервису, любое изменение задевает всё».
3. **Цена бездействия** в метриках, которые уже есть: lead time, число инцидентов, время онбординга, часы дежурств. Даже грубая оценка («около 3 человеко-дней в спринт уходит на обход этого места») убеждает лучше, чем «код плохой».
4. **Предложение с границами:** что делаем, сколько стоит, **как поймём, что сработало** (lead time по checkout вернулся к уровню каталога; ноль инцидентов за два релиза).
5. **Связь с планами бизнеса:** «в Q1 у вас три фичи в checkout — каждая подешевеет».

Отдельная категория — **долг с дедлайном**, который продаётся проще всего, потому что это риск, а не удобство. Пример из Angular: каждая мажорная версия получает около 6 месяцев активной поддержки и 12 месяцев LTS, потом — никаких патчей безопасности. «Если не уйдём с v21 до мая 2027-го, когда у неё закончится LTS, будем жить на фреймворке без патчей безопасности» — это аргумент для аудита и security, а не «хотим новые сигналы».

**Как планировать.** Рабочих моделей три, и их обычно комбинируют:

- **Постоянный бюджет** (часто 15–20 % ёмкости). Плюс: долг гасится непрерывно и не требует торга каждый спринт. Минус: без приоритизации бюджет уходит на любимые игрушки команды.
- **Привязка к фичам** («правило бойскаута» с границами): чиним то, через что проходит текущая задача, и закладываем это в её оценку. Хорошо работает для горячих мест, плохо — для системного долга (миграция стейта, обновление фреймворка).
- **Целевые эпики** под крупный долг с бизнес-кейсом из пункта выше: миграция с NgModule на standalone, выпиливание самописного стора. Отдельная строка в роадмапе, с владельцем и критерием готовности.

Чтобы бюджет не превращался в «пятничный рефакторинг», нужен **реестр долга**: короткая запись на каждый пункт с местом, процентами и ценой погашения. Сортируешь по отношению «проценты / цена» — и спорить на планировании приходится о цифрах, а не о вкусах.

```ts
// Минимальный реестр долга: живёт рядом с кодом (docs/tech-debt.ts или таблица)
type DebtItem = {
  id: string;
  area: string;            // 'checkout', 'shared/forms'
  kind: 'deliberate' | 'outdated' | 'skills-gap';
  interestPerSprint: number; // часы, которые теряем каждый спринт
  risk: 1 | 2 | 3;           // 3 = безопасность / EOL / инциденты
  costToFix: number;         // оценка в часах
  deadline?: string;         // для EOL-долга: '2027-05-01'
};

const priority = (d: DebtItem) =>
  ((d.interestPerSprint * 6) * d.risk) / d.costToFix; // окупаемость за ~квартал

const backlog: DebtItem[] = [
  { id: 'TD-12', area: 'checkout', kind: 'deliberate',
    interestPerSprint: 20, risk: 3, costToFix: 80 },
  { id: 'TD-7', area: 'admin/legacy-grid', kind: 'outdated',
    interestPerSprint: 1, risk: 1, costToFix: 60 }, // уродливо, но почти бесплатно
];

backlog.sort((a, b) => priority(b) - priority(a));
// TD-12: 20*6*3/80 = 4.5 → делать; TD-7: 1*6*1/60 = 0.1 → жить с ним
```

Формула здесь не догма, а способ сделать допущения явными: если продакт не согласен с `interestPerSprint`, вы спорите об одном числе, а не о том, «нужен ли рефакторинг вообще».

**Частые ошибки:**

- «Спринт рефакторинга» раз в полгода: долг успевает вырасти, а бизнес привыкает, что это «отпуск разработчиков».
- Невидимая работа: команда тихо закладывает долг в оценки, бизнес не видит ни затрат, ни пользы — и следующий раз доверия не будет.
- Всё в одной куче: косметика, EOL-фреймворк и дыра в авторизации с одинаковым приоритетом.
- Нет критерия «погашено»: эпик «улучшить стор» не заканчивается никогда.
- Нет отчёта после: если lead time по checkout действительно упал — покажи это. Один закрытый кейс с цифрами продаёт следующие три.

**Зачем это тимлиду:** ты — единственный человек, который видит и код, и роадмап. Если ты не переводишь долг в язык рисков и денег, его либо игнорируют, пока команда не начинает выгорать и уходить, либо гасят хаотично, без пользы для продукта. Умение продать долг — то, что отличает тимлида от «самого сильного разработчика».

**Применить завтра:**

- Заведи реестр: попроси команду за 15 минут назвать 5 мест, где «больнее всего», и для каждого оцените проценты в часах на спринт. Отсортируй по формуле выше.
- Выбери верхний пункт и подготовь питч на одну страницу по пяти шагам (симптом → причина → цена бездействия → предложение с метрикой → связь с планами). Принеси его продакту на ближайшую синхронизацию.
