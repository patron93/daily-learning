# 💻 День 29 · 2026-11-12 · classic: Закон Конвея и Team Topologies — архитектура как копия оргструктуры

**Коротко:** в 1968 году Мелвин Конвей заметил, что системы повторяют структуру коммуникаций организаций, которые их строят. Книга *Team Topologies* (Skelton, Pais; 2-е издание вышло в сентябре 2025) превратила это наблюдение в инструмент: сначала проектируешь команды и их взаимодействия, а архитектура следует за ними. Для тимлида это самая практичная «классика»: она объясняет, почему у вас монолит с вечными конфликтами в `shared/` и как это починить не только рефакторингом.

**Закон Конвея — не метафора, а механизм.** Оригинальная формулировка из статьи *How Do Committees Invent?*: организации, проектирующие системы, вынуждены создавать дизайн, копирующий их собственную структуру коммуникаций. Механизм простой: интерфейс между модулями — это договорённость между людьми. Там, где люди общаются постоянно (одна команда), граница размывается, код связывается сильно. Где общаются редко (разные команды, отделы, часовые пояса), появляется формальный интерфейс: API, контракт, npm-пакет. Поэтому «команда фронтенда + команда бэкенда» почти неизбежно дают систему, где каждая фича режется горизонтально по слою, и каждая фича требует передачи работы между командами: ждём эндпоинт, ждём макет, ждём ревью чужой команды.

**Обратный манёвр Конвея (inverse Conway maneuver).** Если закон работает, его можно использовать: хочешь архитектуру из независимых доменов — сначала собери команды по доменам, дай им общаться в основном внутри, а между собой — через явные контракты. Код начнёт «стекаться» к этим границам. Обратное тоже правда: нарисовать на доске красивые bounded contexts, не поменяв, кто с кем работает, — значит через полгода снова получить спагетти.

**Team Topologies: 4 типа команд и 3 режима взаимодействия.** Книга даёт словарь, чтобы проектировать оргструктуру так же осознанно, как модули.

- **Stream-aligned** — команда потока ценности: ведёт часть продукта (например, «оформление заказа») от UI до БД и отвечает за результат. Это основной тип, остальные существуют, чтобы ей помогать.
- **Platform** — делает внутренний продукт, ускоряющий stream-aligned команды: CI-шаблоны, дизайн-систему, общий Angular-шелл, observability. Ключевое слово — *продукт*: с документацией, версиями и «клиентами».
- **Enabling** — временно помогает другим командам освоить что-то новое (миграция на zoneless и сигналы, внедрение AI-агентов в ревью) и уходит. Не делает работу за них.
- **Complicated-subsystem** — владеет куском, где нужна редкая экспертиза: движок расчёта тарифов, видеокодек, сложный редактор с CRDT.

Режимы: **collaboration** (тесно работаем вместе ограниченное время, чтобы найти правильную границу), **X-as-a-Service** (одна команда потребляет то, что дала другая, с минимумом общения — цель для зрелых границ), **facilitating** (одна команда обучает другую). Главная мысль: режим должен быть **явным и временным**. Если collaboration длится год, граница выбрана неправильно.

**Когнитивная нагрузка — главное ограничение.** Авторы предлагают считать не людей, а объём того, что команда способна держать в голове. Команда в 5–9 человек может уверенно владеть ограниченным числом доменов. Когда команда «отвечает за всё фронтовое», нагрузка перегружена, решения хуже, онбординг дольше. Ответ — не нанять ещё, а сократить зону владения или вынести общее в платформу.

**Как это выглядит во фронтенде.** Границы команд стоит сделать видимыми в коде — тогда закон Конвея работает на вас, а не против. В Nx-монорепо (урок 2026-10-18) теги проектов можно привязать к владельцам, а `CODEOWNERS` — к тем же папкам:

```js
// eslint.config.mjs: правило Nx, где границы модулей = границы команд
rules: {
  '@nx/enforce-module-boundaries': ['error', {
    depConstraints: [
      { sourceTag: 'team:checkout', onlyDependOnLibsWithTags: ['team:checkout', 'platform:*'] },
      { sourceTag: 'team:catalog',  onlyDependOnLibsWithTags: ['team:catalog', 'platform:*'] },
      { sourceTag: 'platform:ui',   onlyDependOnLibsWithTags: ['platform:*'] },
    ],
  }],
},
```

```text
# .github/CODEOWNERS — у каждой папки один владелец
/libs/checkout/      @org/team-checkout
/libs/catalog/       @org/team-catalog
/libs/platform/ui/   @org/team-design-system
```

Если линтер начинает требовать импорт из `team:catalog` в `team:checkout`, это сигнал не «ослабить правило», а обсудить контракт: либо вынести общее в платформу, либо на время включить collaboration между командами.

**Частые ошибки.** (1) Перестроить команды по Team Topologies «на бумаге» и не поменять владение кодом, ревью и on-call — ничего не изменится. (2) Platform-команда, которая делает не продукт, а «тикеты по запросу», становится бутылочным горлышком: её надо оценивать по тому, насколько быстрее стали stream-aligned команды. (3) Микрофронтенды (урок 2026-10-26) без отдельных команд — это распределённый монолит: Конвей всё равно склеит их обратно.

**Зачем это тимлиду:** большинство «технических» проблем — бесконечные мердж-конфликты в общем модуле, фичи, которые ждут три команды, хрупкая общая библиотека — на деле организационные. Тимлид, который видит это, может предлагать решения на уровне структуры (владение, режим взаимодействия, платформа), а не только на уровне кода, и говорить с менеджментом на понятном языке.

**Применить завтра:**

- Нарисуй на одной странице: какие команды трогают ваш Angular-код, кто от кого ждёт работу и в каком режиме они взаимодействуют сейчас (collaboration / X-as-a-Service / facilitating). Отметь места, где режим не назван или «collaboration навсегда».
- Найди 2–3 папки без явного владельца в `CODEOWNERS` или с несколькими владельцами — это кандидаты на конфликты. Назначь одного владельца или вынеси код в платформенную библиотеку.
